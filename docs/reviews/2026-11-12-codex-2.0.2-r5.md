**1. HIGH — A delayed stop task can still revoke a newer kill-switch session. Remaining R4 #2.**

[ConnectionStore.swift:915](native/App/Stores/ConnectionStore.swift:915), [ProfilesStore.swift:895](native/App/Stores/ProfilesStore.swift:895), [TunnelController.swift:1421](native/Packages/TunnelEngine/Sources/TunnelEngine/Controller/TunnelController.swift:1421).

`noteUserStop` queues a task; `userStopped` samples the timestamp when that task eventually runs, not when the owner stopped the session.

Concrete sequence: Cancel A → stop task delayed → authorised on-demand B admitted and observed Connected → stop task runs in a later second and timestamps A’s notice after B’s admission → delivery remains pending → B’s rules are withdrawn and B ends without a user stop → notice arrives. It deletes B’s authorisation; B’s legitimate replay receives 225, leaving the Mac open.

B’s Connected event cannot void a notice that has not yet been queued. No clock rollback is necessary.

**Fix:** Capture cancellation synchronously at the user action and bind it to a root-issued admission generation. Timestamp ordering alone is insufficient. Add a regression that delays notice creation until after B’s admission; the existing test constructs A’s notice before B.

**2. MEDIUM — Pause can turn a refused outside start into a signed restart intent. New-in-round-5.**

[ConnectionStore.swift:618](native/App/Stores/ConnectionStore.swift:618), [ConnectionStore.swift:2245](native/App/Stores/ConnectionStore.swift:2245), [ConnectionStore.swift:2274](native/App/Stores/ConnectionStore.swift:2274).

`crashGapHolder` accepts any owned profile awaiting restart while down. That includes an outside start refused with 225, during the asynchronous interval before its refusal is read. It does not require a previous Connected session or an authorised admission.

A local attacker attempts to start saved manual profile B. While its refusal is being read, the owner confirms an already-open Pause dialog. Pause selects B and signs its resume intent. At expiry, the signed app arms and starts B with the owner’s credentials. Clearing the tentative hold during the signing await does not revalidate the captured target.

**Fix:** Require evidence of an authorised admission before making a crash-gap profile a resume target. Test outside start → gated 225 read → Pause → expiry, asserting no signature, arm or start for B. The new crash-gap test begins with a genuine Connected session.

**3. MEDIUM — Replaying the cancelled admission can void its cancellation. New-in-round-5.**

[ConnectionStore.swift:388](native/App/Stores/ConnectionStore.swift:388), [ProfilesStore.swift:904](native/App/Stores/ProfilesStore.swift:904), [TunnelController.swift:1476](native/Packages/TunnelEngine/Sources/TunnelEngine/Controller/TunnelController.swift:1476).

Every new Connected observation discards pending stops for that profile. However, a `.replay` preserves the original authorisation’s admission time; Connected does not establish a new generation.

Cancel an already-down unattended session while the extension is busy. After the app’s two-second restop window but before its retry, another local user starts that profile using the retained unattended permission. When this replay connects, the app deletes the cancellation. Its subsequent non-user end leaves the permission available indefinitely.

This differs from the intended case where B receives a fresh on-demand or armed admission after A’s cancellation.

**Fix:** Void a notice only after confirming a genuinely newer admission. A replay of the cancelled generation must retain the cancellation. The [Connected-voiding test](native/Tests/LockPlusTests/Round4FixTests.swift:262) emits status changes without establishing a new admission, so it currently blesses this ambiguity.

**4. MEDIUM — Unsigned settings still allow cancellation intent to disappear across relaunch. Remaining R4 #3.**

[AppSettings.swift:267](native/App/Model/AppSettings.swift:267), [ProfilesStore.swift:896](native/App/Stores/ProfilesStore.swift:896).

After a busy Cancel and quit, same-user malware can remove or roll back `pendingUserStops` in `settings.json`. A single malformed entry also makes decoding discard the entire array.

Relaunch then has no cancellation to deliver. Passive reconciliation deliberately preserves the unattended kill-switch authorisation, allowing an outside start with saved credentials despite the owner’s Cancel.

The justification that *forged entries only stop things* misses deletion and rollback of genuine entries.

**Fix:** Keep pending cancellation in protected, rollback-resistant storage until acknowledged or superseded by a fresh authorised admission. Test busy Cancel → quit → erase/rollback queue → relaunch → outside start receives 225. The current persistence test reloads an untampered file.

**5. MEDIUM — Removing the pause expiry bypasses the new one-time-value consumption. Remaining R4 #4.**

[HeadlessResume.swift:94](native/App/Headless/HeadlessResume.swift:94), [ConnectionStore.swift:2490](native/App/Stores/ConnectionStore.swift:2490).

The agent’s `pausedUntil == nil` path unregisters and returns before consuming `.pause`. GUI launch also returns without consumption.

Same-user malware copies a genuine pause, removes `pausedUntil`, and lets the GUI or agent observe that nothing is paused. Restoring the genuine record and original expiry later, within seven days, still verifies and makes the signed app arm/start the saved profile.

**Fix:** Consume the outstanding pause value on terminal “nothing paused” paths too; preserve a retry when consumption fails. Test removal of the expiry followed by actual restoration and relaunch. The new nil-profile tests retain the expiry and miss these early returns.

**6. MEDIUM — An answer being saved escapes invalidation when a new payload commits. Remaining FIX4/Fable N2.**

[TunnelController.swift:1813](native/Packages/TunnelEngine/Sources/TunnelEngine/Controller/TunnelController.swift:1813), [TunnelController.swift:2010](native/Packages/TunnelEngine/Sources/TunnelEngine/Controller/TunnelController.swift:2010).

For a before-Connected answer with `save == true`, `answerAuth` removes `broker.live`, then awaits credential storage before creating `s.answer`. During that await, the commit handler sees neither a live prompt nor a stashed answer and does nothing.

Sequence: revision-1 server A prompts → submit a static-challenge answer with Save enabled → credential operation suspends → revision 2 for server B commits → answer resumes. The session/phase checks still pass, and the next attempt loads revision 2 with A’s answer, including its response, overriding the newly provisioned credentials.

**Fix:** Bind in-progress answers and saves to the payload/attempt generation, invalidate them on commit, and recheck after awaits. Block credential saving in the regression, commit revision 2, then release it. The [current test](native/Packages/TunnelEngine/Tests/TunnelEngineTests/Round4ControllerTests.swift:101) commits while the prompt remains live and submits the answer afterward.

**7. MEDIUM — An unavailable launch check can permanently skip the owed “Off” seal. Remaining FIX4/Fable N4.**

[ProfilesStore.swift:194](native/App/Stores/ProfilesStore.swift:194), [ProfilesStore.swift:148](native/App/Stores/ProfilesStore.swift:148).

When Auto-Connect is disabled and `checkRecord` returns `.unavailable`, verification marks the choice trusted without scheduling a seal. Subsequent loads skip verification, and `retryOwedSeal` has nothing to retry.

Concrete sequence: copy an enabled record → owner turns Off while the keychain is unavailable → quit before a successful seal → relaunch while it remains unavailable → unlock and reload. Off is never sealed in that run. Restoring the copied enabled record at the next launch restores Auto-Connect.

**Fix:** Keep verification pending, or mark the disabled choice’s seal owed, on `.unavailable`. Extend the [seal retry test](native/Tests/LockPlusTests/Round4FixTests.swift:277) across relaunch and keychain recovery; it currently exercises an explicit retry in one process.

FIX4’s remaining-refusal list does **not** establish an unconditional kill-switch restart guarantee:

- Owner stop/Delete/wipe/configuration removal are legitimate exceptions only for the intended admission. Finding 1 violates that qualification.
- Failed writes and corruption remain fail-open limitations. [State saving](native/Packages/TunnelEngine/Sources/TunnelEngine/Controller/TunnelStateStore.swift:129) logs failure without making admission depend on durable authorisation.
- [Capacity eviction](native/Packages/TunnelEngine/Sources/TunnelEngine/Controller/TunnelController.swift:1494) still removes recoverable kill-switch records when only those remain. Its test checks selection order, not a 257th admission followed by the victim’s replay.
- Whole-second rounding preserves some explicitly cancelled admissions. Clock rollback is not the only way to revoke a newer one; finding 1 needs no rollback.
- Rejecting a positively different boot remains reasonable under the stated NE behaviour.
- The [120-second orphan grace](native/App/Stores/ProfilesStore.swift:279) merely delays deletion during a longer offline restart gap. Its test expressly expects deletion after 121 seconds. Preserving recovery requires explicit retirement, not elapsed time alone.
- Standing unattended permission remains the documented NE-replay ambiguity; it does not justify losing explicit owner cancellation.
