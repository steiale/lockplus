Deferred-removal branch (`onDemandHeldBack`) still excludes the profile's own live status, correct since the removal is deferred only when ANOTHER profile is busy.
- **LOW 1 (U10 over-trigger / copy / no Cancel / PF 53) — closed.** Distinct `.mayRestart` reason, hedged copy, Cancel allowed (`DerivedState.swift:223`), `crashes.crashed` recorded; quiescer uses `stopAsUser` so a sticky 12 is never read for its stops; delete's stop is a user stop too. - **Test gaps — closed** (unwatched teardown busy, teardown timer, U10 ended by NE restart / Cancel, with-rules negative, quiesce as user stop, delete lost/delivered `.disconnected`). Remaining gaps below.

## 2. Regressions / residuals (all LOW)

**L-A. `dropVanished` trusts a single reload; a partial `loadAllFromPreferences` would end a live kill-switch session's bookkeeping and let the restore save inside it.** `ManagerStore.swift:398-418` (`loadUnlocked` → `reportEnd`), `ConnectionStore.swift:890-909`. A failed reload is safe (`NEManagerStore.loadAll` throws before `byID = map`, `reported` untouched). An EMPTY list is also safe (no manager to restore onto; `restore()` only drops the record, `wantsRestore` re-restores at the next load). Only a PARTIAL list (the live manager missing, the auto one present) → `.invalid` → `sessionEnded` → not busy → `restore(auto)` saves on-demand beside the live kill-switch session (E2E-3 trigger). No evidence in `docs/native/reference/networkextension.md` or RESULTS-E2E-4 (U3/U13 show complete lists) that NE ever returns partial lists; before this commit the same case was fail-closed-forever (the HIGH). Unverified residual. Cheap hardening: in `loadUnlocked` only `reportEnd` for an id that is missing in two consecutive loads (keep the `remove` path immediate: that removal is certain); and note it in DESIGN §10.4 residuals.

**L-B. `.invalid` as a session end relies on NE never reporting `.invalid` transiently for the current connection object of a live manager.** `ConnectionStore.swift:245-246, 274-286`; `TunnelStatus+NE.swift:7,13`. Reference doc has only "0 `.invalid` (not configured)"; S2 E9/U7 saves on connected managers were measured for session survival, not for status notifications. If a save of a `.connected` manager (on-demand/rule/name, U7 heal) ever emits `.invalid` on the same connection object: pre-commit the restore already ran (`.invalid` was never live), so the save-inside-session risk is NOT new; what IS new: `sawActive` is dropped, so the following `.connected` reads as a new session (duplicate `.connected` notice, `sessionKillSwitch` re-read from possibly drifted flags (N6), `attemptStartedAt` reset for M8, `onObservedDisconnect` fired → AuthCoordinator drops a prompt). Also `@unknown default → .invalid` now ends a session on any future NEVPNStatus case. Fix (loses nothing): treat `.invalid` as an end only when the manager is gone (`!known.contains(id)`, already covered by `dropVanished`) or the previous handled status was `.disconnecting` (LOW 3); otherwise log and keep `sawActive` (a real removal is caught at the reload anyway). Worth one E2E probe: save on-demand on a connected manager and log every status event.

**L-C. `dropVanished` skips `sessionEnded`'s bookkeeping for the vanished case.** `ConnectionStore.swift:199-204` sets `statuses[id] = .invalid`, `dropVanished()` removes `sawActive` first, so at `:246 sessionEnded(id)` the `sawActive.remove(id) != nil` branch is skipped: no `resetSnapshotEpoch()`, `restartedAfterCrash` not cleared, no `onObservedDisconnect?(id, nil)` (AuthCoordinator keeps a prompt of a session whose configuration another admin removed mid-start via System Settings, U3). Fix: route stale ids in `dropVanished` through `sessionEnded(id)` (one end path) instead of hand-copying the resets.

**L-D. `stopAndWait` does nothing for a deleted profile whose start is pending but not yet live.** `ConnectionStore.swift:327` guard returns true at once; `stopAsUser` (which would clear `.starting(issued:false)`/`.waitingForStop` for that id) never runs. Delete during the profile's own prepare → `onDemandHeldBack(id)` is false (only its own entry) → `managers.remove` runs while `startNow` continues → `prepareForStart`'s save can re-create the configuration as a fresh `NETunnelProviderManager` after the removal (orphan until the idle sweep), or `managers.start` throws `profileNotProvisioned`. Deleting a switch TARGET (`.waitingForStop(of: old)`) leaves the entry; at `old`'s `.disconnected` the deleted profile is started (`profiles.profile(id)` nil skips prepare, `managers.start` still runs on the deferred-removal manager; fails in the extension). Pre-existing (old `delete` checked `managers.status` the same way), but `stopAndWait` is the natural place now. Fix: `guard ... || pending[id] != nil`; `stop()` already resumes the waiter at once when the status isn't live.

**L-E. `.mayRestart` Cancel: honest copy, but Cancel does not stop NE's restart, only the wait.** `ConnectionStore.swift:1018-1026`. `disconnect()` → `stop(id)` (`stopVPNTunnel` on a `.disconnected` connection is a no-op) → `restoreIfIdle()` restores on-demand at once. If NE then restarts (window ≈ 1 s after `.disconnected`, U8), the restore's save lands inside the restart (the E2E-3 trigger the hold exists for; fail-closed, not a leak), the restarted session shows Connected, and within 2 s of `userStopsAt` it is bookkept as user-stopped (no crash handling at its end). In practice unreachable: the hold is armed ~ms after `.disconnected`, NE restarts at ~1 s, a human Cancel comes later. Copy ("Checking whether X restarts…" / Cancel) doesn't claim to prevent the restart; acceptable. Optional hardening: on an active status for a profile in `userStops` with `userStopsAt` ≤ 2 s and no own entry, stop it again (the user said Disconnect), or label the action "Stop Waiting".

**L-F. A user stop during an NE-initiated `.disconnecting` leaves the `holdTeardown` entry until its 22 s timer.** `observedDisconnect` `:340-347` returns in the user branch without clearing the `.awaitingRestart` armed at `:267`. Now reachable via `stopAsUser` too (quiesce/delete during a teardown): for delete, `dropVanished` clears it (manager gone); for quiesce the hold lingers 22 s (moot under `extensionHandOver`; a `resumeAfterUpdate` `connect(target)` for a DIFFERENT target within 22 s would be ignored with a "wasn't reconnected" note). Pre-existing from e321e10. Fix: in the user-stop branch (or in `stopAsUser`), `if pending[id]?.phase == .awaitingRestart { clearPending(id) }`.

**Checked, no issue:** `delete` → `stopAndWait` closure wiring (`AppEnvironment.swift:175-178`, set for all modes incl. preview; nil only for a bare `ProfilesStore`, i.e. the read-only headless agent, which never deletes). 10 s timeout: on expiry the removal proceeds and `remove` synthesizes `.invalid`; `onDemandHeldBack` still defers the removal while another profile starts/lives (a Connect of B waiting on A's stop → `waiter(for: A)` → `startNow(B)` at A's `.disconnected`/`.invalid`, removal deferred to the idle sweep). Continuation ordering: `stopAsUser` spawns `stop()`'s Task but `waitForSessionEnd` appends its continuation before any suspension, so the "already down" resume at `:1051` can't be lost. `stopAsUser` in the quiescer: now asynchronous (`stop()`'s Task) but the 15 s poll covers it; other users' managers were stopped before too. `connectHold`/`mayBeRestartedByNE` consistent with `CrashRestartPolicy.decide` (`onDemandEnabled`, session-time kill switch). No lock re-entrancy: `reportEnd` inside `locked` only spawns Tasks (`startNow`, `restoreIfIdle`) that queue behind the lock. `.mayRestart` surfaced everywhere (`startHold`, UIBinder, copy, xcstrings, help).
