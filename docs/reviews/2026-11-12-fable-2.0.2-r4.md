# LockPlus 2.0.2 security review (Fable, round 4)

Scope: `git log cddbde38..3bae248d` (9 commits, HEAD 3bae248d), read-only. Paths are relative to `native/` unless they start with `docs/`.

What this rests on:
- Reading the fix diffs, the code around them, the new tests and DESIGN draft 10.7.
- Extension side: I ran tests on a scratch copy of `Packages/TunnelEngine` + `Packages/LockPlusCore` (deleted afterwards, repo untouched). `Round3ControllerTests` pass (8/8). Two probe tests of my own reproduce L1. Three mutations (see task 1) are each caught by the existing tests.
- App side (`App/`, `Tests/LockPlusTests`): read only, nothing run. Nothing was run against real NetworkExtension; NE behaviour is taken from the project's notes.

## Verdict

No HIGH. No MEDIUM. Three LOW, six NIT.

- Every round-3 finding (mine and Codex's) is fixed for the scenario described. All have a regression test except the app's Cancel-of-recovery path (L3).
- Codex's HIGH is closed for a start in flight or held. The same failure is still reachable for a kill-switch start that is still in the guard (L1): much narrower window, same outcome.
- The user-stop notice cannot be used by another user or by same-user code to kill a running session's record. Its gaps all fall back to the round-3 state (the record stands), never to an open Mac (L2).
- Start authorisation (item 3): release-ready for the RC. I would not cut it on review grounds. See task 4 for the conditions.

## LOW

### L1. A profile change still fails a kill-switch start that waits in the guard on an ending session (remaining; rest of Codex r3 #1; reproduced in the test harness)

- `Packages/TunnelEngine/Sources/TunnelEngine/Controller/TunnelController.swift:1965`: `payloadCommitted` still invalidates every guarded start of an older revision, kill switch or not. The start throws `.startCancelled` at `:341`.
- FIX3 and D10.7-1 justify this with "each waits beside a live session of its own profile, which goes on protecting". That holds for the duplicate wait only. Two other guard waits have no protecting session:
  - `:365`: any start waits while the incumbent session is `.stopping`, whatever its profile.
  - `:400`: the start tears down a stale session (`await stop(reason: .superseded)`), which is NE's restart in the same process after it stopped the old instance.
- Scenario: kill-switch profile P connected at revision 1. Save Only of revision 2, not yet verified. NE restarts P (stop of the old instance, start of a new one). While the new start waits for the old adapter's teardown, the background check accepts revision 2 and the app provisions it. NE's authorised replay ends with `.startCancelled`; a failed `includeAllNetworks` start leaves the Mac open, and nothing starts P again.
- Reproduced with two probe tests on the scratch copy, both ending in `.startCancelled`:
  - a kill-switch start of profile B waiting on profile A's fatal teardown, then `profileProvisioned(B, revision: 2)`;
  - an armed kill-switch session, `providers.stopped(a)`, the replay with the persisted nonce on a new instance during the hung teardown, then `profileProvisioned(revision: 2)`.
- LOW, not higher: the window is the local teardown (normally well under a second) and a network attacker can't stretch it or trigger the commit. Background provisioning is new in 2.0.2, so commits now happen at moments the user didn't choose.

Fix: record the kill switch in `GuardedStart` (`req.includeAllNetworks || cfg.policy.killSwitch`) and never invalidate such a start on a commit; it proceeds and loads the committed payload, as the held start now does. The duplicate case may keep ending (it has a protecting session), but one rule for all kill-switch starts is simpler. Tests: the two probes above with the expectation inverted.

### L2. A user stop is not always told to the extension (new in round 4; the fix for Fable L1 / Codex r3 #3 is incomplete)

In each case the record stands as before round 3: one outside non-manual start is admitted until reboot. Nothing is left open.

- **a. Before a successful hello.** `App/Stores/ProfilesStore.swift:844` drops the notice when `extensionCapabilities` is nil; it is not queued. `App/AppEnvironment.swift:443`: a failed hello is not retried in this run, so every notice of the run is dropped. Scenario: relaunch offline with "connects when a network is available", Cancel before the hello returned (or after it failed).
- **b. Not durable.** `pendingUserStops` is memory only (`ProfilesStore.swift:848`). Cancel, a busy extension, then Quit: the notice is lost.
- **c. The headless agent.** `App/Headless/HeadlessResume.swift:128` and `:192` stop a held profile "as the user would" and send no notice.
- **d. Pause in a crash gap.** From reading: `pause()` (`App/Stores/ConnectionStore.swift:2255-2295`) stops only a live session, an issued start or the network-restart hold. A profile in `.awaitingRestart` is neither stopped nor notified.

Fix: always insert into `pendingUserStops` and gate only the send; persist the set in `settings.json` (a forged entry only ends a record of a profile that is not live, which same-user code can do with `scutil --nc stop` anyway) or flush it on quit; send a notice from the agent's two stops. Tests: a stop before the first hello is delivered after it; the agent's stop of a hold reaches the service.

### L3. The app's Cancel-of-recovery notice has no regression test (new in round 4; test gap)

- `Tests/LockPlusTests/Round3FixTests.swift:146` (`everyUserStopIsToldToTheExtension`) covers only Disconnect of a live session, the one case where NE's own `stopTunnel` clears the record anyway.
- The finding itself was the stop of a session that is already down: `ConnectionStore.swift:874` (`stopNetworkRestart`). No test references `userStoppedProfileIDs` on that path, nor on Pause, Delete or a switch. Removing line 874 passes the suite.
- The extension half is tested and mutation-checked (`aUserStopOfASessionAlreadyDownEndsItsKillSwitchRecord`).

Fix: one app test per path. At least: `noNetwork` hold, Cancel, expect a revoke request naming the profile.

## NIT

- **N1. Stale notice (risk 30 (1), remaining).** `ProfilesStore.swift:851`: only a LockPlus Connect voids a pending notice. Void it on any live status of the profile too, or send the stop time and let the extension skip a record admitted after it. Either closes the path.
- **N2. A kept kill-switch start at a prompt (new, from reading).** After a commit the start is kept, and its live prompt with it. The answer (`TunnelController.swift:1789`: carried username, password, challenge cookie of the old revision's server) is used by the next attempt on the new revision. The new revision is the owner's own edit, so no attacker gains from it. Resolve the live prompt on a commit and prompt again.
- **N3. `userClearedAt` grows without bound** (`TunnelController.swift:1417`): one entry per UUID the app ever names, in a root process. Only the signed app can add entries. Drop the map when no start is in the guard.
- **N4. An "off" that can't be sealed** (`ProfilesStore.swift:141-146`) clears the tag but leaves the old one-time value, so a copied enabled choice still verifies at the next launch. Needs a keychain write failure at that moment. Keep a "seal owed" flag and retry.
- **N5. Reconcile removal in a gap the app doesn't track** (`ProfilesStore.swift:1024`, remaining). `isLive || revocationHeld` misses NE's restart gap when the app was launched inside it or its `.awaitingRestart` timed out. Only for a profile whose file vanished (same-user tampering); a user Delete stops the session first.
- **N6. Small ones.** `ProfilesStore.swift:820`: above 10,000 keeps nothing is sent, the user stops included; send those on their own. `ConnectionStore.swift:581`: `consumeHoldRecord` joins the chain one task hop late, so a hold sealed right after can lose its value and be dropped at the next launch (does less, never more).

## Task 2: what the round-3 fixes introduced

- **User-stop notice, who can send it.** Only a peer that passes the extension's code-signing requirement, and only for its own uid (`EngineServiceBackend.swift:132`, `peer.uid`). Another user reaches only their own keys (tested). The app has no URL scheme, AppleScript or App Intent, so same-user code can't make it send one.
- **Can it kill a running session's record?** No. The live key is skipped (`TunnelController.swift:1407`), a start admitted meanwhile is live, and pending arms stay. A replay waiting in the guard is refused only when no session of that profile is live, which is a real user stop.
- **Can it block a legitimate restart?** Only through a stale notice (N1, risk 30 (1)).
- **Retry and cancel.** One revoke at a time; a failed send keeps the stops; a Connect voids them. A page-0 notice can be applied twice when a later page fails, with no effect beyond N1. Gaps: L2.
- **Sealed Auto-Connect and the first-launch seal.** Sound. The one-time value is in the data-protection keychain under the app's access group, so same-user code can't delete the "initialised" marker to reopen trust-once. Every settings change reseals, including the forced "off" after an invalid tag. Only N4.
- **Sealed `networkRestartHold`.** Sound. An unverified hold only holds the restore back and can be stopped; it is never signed, and its timeout starts nothing. The agent uses the hold unauthenticated, but only to stop or defer.
- **One-time values consumed at every end.** Correct in the GUI, the agent and the update resume; `.unavailable` is excepted. No new replay found. Same-user code can make a pause end without reconnecting, which it could before by editing `settings.json`.
- **Provision no longer ending kill-switch starts.** No stale or rejected payload runs: the attempt in flight uses the payload it loaded (an approved, provisioned revision), and a hold's next attempt loads the committed one, which only a verified profile produces. This is the state a Save Only on a connected session already gives. Side effects: N2, and the miss in L1.
- **Paged revokes.** The union is applied only when complete, only the newest batch counts, a single-page request drops a partial one, and memory is bounded (20 × 500 per uid). A stale keep set can't hurt: live, guarded and kill-switch records are skipped by the extension anyway.
- **Private read queue.** The hung count is exact in both orders; at most 4 hung threads plus the one in flight. No finding.
- **Validator expected-exit window.** A crash is never turned into "accepted": every path retries or throws. The window is consumed once, so a hostile file gets at most one free retry per watchdog timeout (8 s each), with no loop.

## Task 3: the remaining refusal paths (end of FIX3-REPORT)

1. **The user's own acts.** Right by design. A stop that lands on another live instance's session returns before anything is cleared.
2. **Lost record and the 256 cap.** Acceptable. Another local user who can start their own tunnels could push a record out during an offline gap, but that user can already hold a kill-switch session of their own, which is worse and pre-existing (risk 23).
3. **Stale notice, risk 30 (1).** Acceptable for the RC. It needs a failed delivery, a start outside LockPlus, a non-user end and a configuration without rules, in that order. N1 closes it cheaply; do it in 2.0.3 at the latest.
4. **Record of another boot.** Right.

Missing from the list: L1 (a commit during a guard wait) and N5 (reconcile removal in an untracked gap). The report's last sentence, "background provisioning … no longer touch a kill-switch session's start", is not yet true.

## Task 4: is start authorisation release-ready?

Yes for the release candidate. I would not cut it to 2.0.3 on review grounds.

- Four rounds went from several HIGHs to none. What is left in item 3 is L2, L3, N1, N3: each falls back to "the record stands" (still stricter than 2.0.1, which had no authorisation at all), not to a wrongful 225.
- The outcome that would be worse than 2.0.1 is a wrongful refusal of NE's restart. The paths I know are the four in task 3, all needing a user act or a rare chain.
- L1 belongs to item 1 (background provisioning), which isn't cuttable. Cutting item 3 would not remove it. Fix it before the RC: it is a few lines and the tests exist as probes.

Conditions:
- Everything here is fakes. D-6 stays the gate: E2E-8 S6/S8 and the new rows C1, L1, N1, M1 on real NE. Any 225 on NE's own restart of a kill-switch session (crash, sleep/wake, Wi-Fi off and on) is a cut unless the fix is trivial.
- Fix L1 and add the L3 test before the RC. L2 can ship as a documented residual if time is short; a and c are small.
