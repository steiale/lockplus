**Verdict: nothing above LOW remains.** The two layers close the measured 200011 gap on our own Connect (path check, then the `.disconnecting`-first refusal → `.startEndedEarly` → code 2 → `.awaitingNetworkRestart`), NE's own restart (active status ends the hold; no restore inside it), a relaunch (record re-entered before the launch restore; fallback arms only after a reading with an interface) and the headless agent (live → leave alone; coming → stop before restore). The invariant holds on every path I could construct: no save/removal/on-demand enable of another own manager runs between the pause and the session's end, no weaker flags are saved, and every hold that keeps auto-connect off has a row 12a line with Cancel (DerivedState.swift:223 offers Cancel for both new reasons). Findings, most severe first:

**L-1. System Settings refusal while the app runs is not held, and the test models an unmeasured sequence.** `native/App/Stores/ConnectionStore.swift:306-315`: a refusal is delivered as `.disconnecting` → `.disconnected` only (RESULTS (a)); a start made elsewhere has no entry and is never in `sawActive`, so `holdTeardown` (line 339) and `observedDisconnect` are skipped and `restoreIfIdle` runs at the `.disconnected`. NE then restarts it when an interface returns beside whatever was restored. Consequence is narrow (only a pause record pending a failed-restore retry can be restored at that moment; otherwise it is the pre-existing "session started elsewhere, nothing paused" class), but the commit/DESIGN claim "any watched session (NE's, System Settings', ours seen active)" overstates it, and `NoNetworkRestartTests.swift:173-192` emits `.connecting` first, which measurement (a) says never arrives, so it passes through `sawActive`, not through the refusal path. Fix: in the `.disconnected` branch, also treat `previous == .disconnecting && !sawActive && pending[id] == nil && !userStops.contains(id) && mayBeRestartedByNE(id)` as a possible refusal (`checkNoNetworkRefusal(id, holdForSystemRestart(id, recordCrash: false))`), or narrow the doc/claim to our own start + sessions seen active; change the test to the measured sequence.

**L-2. Connect of another profile during the refusal's `.disconnecting` window starts beside NE's pending restart.** ConnectionStore.swift:259-261 clears the issued entry at `.disconnecting` and `holdTeardown` (339) needs `sawActive`, so for ~1 s there is no entry (busy only by status); `connect()` (795) takes a Connect as `.waitingForStop(of: X)`, and at X's `.disconnected` line 314 arms the hold and line 317 starts the waiter at once, so its prepare/pause saves run while the code-2 read is pending and NE's restart of X is armed for the next interface. Fix: in the `.disconnecting` branch, arm a teardown entry for `issuedEnding` too (`arm(id, .awaitingRestart, timeout: stopTimeout)`), so the Connect is ignored and the UI holds it; and skip `startNow(target)` at 317 when a hold was just armed for `id`.

**L-3. Network-return start bypasses `connect()`'s pre-checks.** ConnectionStore.swift:449-456 calls `startNow(id)` directly, without the active-profile (`beginSwitch`, line 782) and `stoppingOther` (795) checks. NE's on-demand start of the auto profile lands ~1 s after the interface, ours at +2 s: the prepare and pause saves then run beside auto's `.connecting` session until F6 (883) switches it out; a session `.disconnecting` at that moment gets our `startVPNTunnel` inside NE's Stopping (S2: silently dropped, 30 s `startingTimeout`, fail closed). Fix: route the resume through the same checks as `connect()` (extract the tail of `connect()` from line 782 on into a helper used by both).

**L-4. `pause()` leaves the hold record durable while the pause is recorded; relaunch re-enters it during the pause.** ConnectionStore.swift:1452-1460: the durable write (pausedState, record cleared) precedes `stopNetworkRestart(held)`, whose `forgetNetworkRestartRecord` (409) is a queued write. A crash in between leaves `pausedState.profileID = X` and `networkRestartHold = X`; `resumeNetworkRestartAtLaunch` (467-479) ignores `pausedUntil` and re-enters the hold although the stop was issued, and the later `resume()` → `connect(X)` is ignored by the guard at 764 with no note (the `other` at 1491 is nil for the same profile), so X is not reconnected and nothing says so. Fix: clear `networkRestartHold` inside the durable write at 1452 when `held != nil`; skip re-entry at launch while `pausedUntil` is set; in `returnOnDemand`, note the target when its own hold ignored the Connect.

**L-5. Headless: `held == target` and live loops instead of completing.** `native/App/Headless/HeadlessResume.swift:94-97`: a live held session that is the pause's own target (pause() sets `profileID = live ?? held`) returns `.networkRestartPending` every minute for as long as X runs (a kill-switch session: until the user stops it) with the pause expired and the other on-demand IDs off, instead of the existing "target already live" path (line 120: nothing verified or started, owed recorded, pause cleared, agent unregistered). The GUI's launch resolves it. Fix: `if managers.status(held).isLive && held != target { return .networkRestartPending }`.

**L-6. Hold armed before the durable write.** ConnectionStore.swift:394-396: `armNetworkRestart` then `await updateDurably`. A crash in the gap leaves no record and the launch restores beside NE's restart. The caller's entry (the `.startEndedEarly` hold with its 10 s timer, or the fetch entry with 15 s) already blocks the restore, so the write can come first. Fix: swap the two lines (re-check the token after the await before arming).

**L-7. Sticky code 2 after a connected session.** ConnectionStore.swift:634-635: measured (e) says a connected session losing the network goes `.reasserting`, never `.disconnected` with code 2, so code 2 read at the end of a session that reached `.connected` is stale (an earlier refusal or Cancel) and the hold (≤ 10 s with a network, unbounded without) is for a restart that will not come, while row 12a says "X connects when a network is available". Fix: add `!wasConnected` to the condition; keeps the net for never-connected ends. Also `observedError` (691-703) maps code 2 to `.engineFatal` "NEVPNConnectionError 2", which row 14 shows after the hold ends; map it to a "no network" message.

**L-8. UI/store mismatches.** (a) ConnectionStore.swift:757-759 stops X before the `engineVerified` guard at 777: an unverified other profile cancels NE's restart and then fails, leaving nothing. Move the `stopNetworkRestart` after the guards. (b) `connectHold` (1189) returns nil for another profile's Connect whenever the hold is `.awaitingNetwork`, but `connect()` (757) only stops X when `pending.count == 1`: with a second entry (another session's teardown hold) the button is offered and the Connect ignored. Return the hold when `pending.count > 1`. (c) `holder(of:)` (1040-1042): `.awaitingNetworkRestart` counts as `starting`, so `aboutTo` is true when the auto profile's on-demand is ON (nothing was paused for a session started elsewhere) and the pane names X as the holder though no pause is coming; exclude it from `aboutTo`, keep it for `recorded`.
