**L-1. L-E re-stop can fight NE's on-demand (stop/start loop).** `ConnectionStore.swift:238-243` stops any active status within 2 s of a user stop with no entry, `suspending: false`. After Cancel of a `.mayRestart` hold, `disconnect()` (`:1076-1084`) runs `restoreIfIdle()`, which can turn THIS profile's on-demand on (Auto-Connect toggled to it during the hold; a stay-connected profile; a previously failed `restoreOwnOnDemand`). NE's on-demand start lands within 2 s → re-stop (od untouched) → on-demand again → each `stop()` resets `userStopsAt` → loop as long as traffic triggers. Fix: guard the re-stop with `managers.managers.first { $0.profileID == id }?.onDemandEnabled != true` (NE's crash restart never happens with rules on, S2 E1+od, so an active status with od on is an on-demand start the app itself re-enabled), or stop with `suspending: true`. Otherwise L-E is right: a user Connect has an entry (`hadEntry`), `userStops` is cleared at the handled `.disconnected`, the `sawActive` guard keeps it off during a teardown.

**L-2. **L-3. The `issuedStartEnded` hold records a crash for what may not be one → false PF 53.** `ConnectionStore.swift:224, 270, 302-305`. So an LP error at `.disconnected` means a stop/removal, which NE does not restart. Residual only if NE ever failed to record 12 for a death; the nil branch would still hold.
