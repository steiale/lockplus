## LOW

### L1. Pause still signs a start made elsewhere while it is `.connecting` (remaining part of Fable r5 L2 = Codex r5 #2; from reading)

- `App/Stores/ConnectionStore.swift:2250-2251`: `live = statuses.first { $0.value.isActive }`, then `active = live ?? signableHold`. `isActive` includes `.connecting` (`:2720`).
- The new `resumableSession` filter applies only to `signableHold`. A live session is signed without it, here and again after the write (`:2307`, `liveNow ?? signable`).
- A start made elsewhere is removed from `resumableSession` at its first active status (`:361`), so the set already says "not ours, never connected". Pause doesn't ask it.
- Scenario: nothing is connected. Another local user loops `scutil --nc start` on the owner's kill-switch profile P. Each attempt is refused (225), but P is `.connecting` while the provider starts and refuses. The owner presses Pause in such a window. Pause signs P; at the pause's end LockPlus arms and starts P with the saved credentials.
- This needs NE to deliver the attempt's `.connecting`. The code expects that it can (`:333-334`, "a refused start's `.connecting`").
- Same class and same rating as round 5's L2: it needs the owner's Pause while the hero shows P connecting, and it starts only the owner's own verified profile. The code path predates this round.
- Three sentences are wrong while this stands:
  - DESIGN D10.9-2.
  - DESIGN risk 31 (b): "Pause signs only a session this run started or saw connected".
  - The CHANGELOG line "A start from elsewhere that was refused is stopped by the pause and not reconnected".

Fix: sign a live session only if `resumableSession` contains it, at both places; still stop it in every case. At launch, also insert a session found `.reasserting` (it was connected). Test: `emit(P, .connecting)` with no issued start, Pause, expect `pausedState.profileID == nil` and no arm or start at the end.

### L2. A same-revision retry no longer ends a split-tunnel start that already loaded the new payload (new in 8d233e25; reproduced)

- `Packages/TunnelEngine/Sources/TunnelEngine/Controller/TunnelController.swift:1983`: the commit is now compared with `s.loadedRevision` for every session. Fable r5 N2 was only about a kept kill-switch start at a prompt.
- Before, a start without a kill switch under NE configuration revision 1 that had loaded payload revision 2 was ended by the next commit of revision 2 (`2 > cfg.revision`). That was round 6's Codex M2 rule; the comment at `Service/EngineServiceBackend.swift:166-169` still describes it.
- Now `2 > loadedRevision (2)` is false and the start goes on.
- Scenario:
  1. A provision of revision 2 stores the payload; its credential write fails.
  2. A start under the old configuration (on-demand, or made elsewhere) loads payload 2 with revision 1's stored credentials.
  3. The app's retry commits revision 2 again. The start is not ended and sends the old credentials to the new revision's server.
- Probe on the scratch copy: after the same-revision commit the phase is `.connecting` on HEAD, and `.idle` with the old comparison.
- LOW: no attacker controls it, the window needs a failed credential write, and a kill-switch start already behaves this way by design (D10.7-1). But it reverses an earlier fix without a test or a mention in D10.9-4.

Fix: keep `revision > s.loadedRevision` for the kill-switch branch only; the branch without a kill switch compares with `cfg.revision` as before. Test: my probe (provision 1, store payload 2, start, `payloadCommitted(2)`, expect the start ended). Otherwise state the narrowing in D10.9-4 and fix the backend comment.

## NIT

- **N1. The save's revision re-check is not atomic with its write (new, theoretical).** `TunnelController.swift:1845-1848`: `saveAnswer` checks the payload revision again and then calls `secrets.put`. A provision of revision 2 that lands on the store between the two is overwritten by credentials tagged revision 1. It needs the commit to overtake a continuation that is already queued on the controller. The answer itself is never used. A full cure is a conditional put in the store.
- **N2. Test gaps (mutations that survive).**
  - M1 and M9: the `answerInFlight == promptID` checks in both answer paths can be removed and the suite passes; the shipped test is saved by the phase check. The check matters when the fresh attempt has prompted again before the save returns. My probe of that sequence passes on HEAD and fails under M1.
  - M3: the first revision check in `saveAnswer` is untested. Its visible effect: an answer with Save to a prompt after Connected is silently not saved once a Save Only revision was installed during the session.
  - App side, from reading: the two `resumableSession.remove` lines (`ConnectionStore.swift:361`, `:415`) can be removed and `aRefusedOutsideStartPausedInItsHoldIsNeverSigned` still passes, because its profile was never in the set. Add the realistic order: Connect P, Disconnect, then the refused outside start, then Pause.
- **N3. The real keychain is still a default argument.** Details in "Test hosts and the real keychain" below.
- **N4. Wording.**
  - Risk 29 (1) says the rules "went away while it ran". Rules withdrawn while the session is down in the gap leave the same standing record.
  - Outside the diff, older: `resume()` ignores a failed `consumeRecord` (`ConnectionStore.swift:2418`, `:2429`); a delete that fails right after a successful read leaves the value usable.

## (a) Is the removal complete?

Yes.

- No reference is left to `userStopped`, `UserStopNotice`, `pendingUserStops`, `noteUserStop`, `endedByUserStop`, `replayOf`, `tellUserStop`, `deliverUserStops`, `userStarted` or `notices(` in `native/` sources, tests or scripts. DESIGN mentions them only in the revision log and the struck-through entries.
- Extension: a kill-switch record is now cleared only by:
  - `stop(.userInitiated)` and `stop(.configurationRemoved)` of the running session;
  - `profileRemoved` and `secretsWiped`;
  - the next boot;
  - cap eviction.
- The guard refuses a waiting replay only through `userClearedSince`, which those live acts set. No path clears or refuses by time any more; `AuthorisedStart.at` is read only by eviction. Round 5's L1 is moot, as FIX5 says.
- Round 3's N1 is intact: mutation M8 (disable `replayEndedByUser`) fails `aReplayWaitingInTheGuardIsRefusedAfterTheUsersStop` and `userClearMarksAreKeptOnlyWhileAStartIsInTheGuard`.
- Wire: `keepProfileIDs` is required at decode. A stop-only body is refused, not read as an empty keep set (mutation M7 caught by `aRequestWithoutAKeepSetIsRefused`). The decode fuzz passes.
- App: the three stop paths (`stopNetworkRestart`, `stopAwaitedRestart`, `stop`) keep their `managers.stop` and settle logic. The agent's two stops of a held restart remain. The hello retry and reconcile are unchanged. An unknown `pendingUserStops` key in a `settings.json` from a round 3–4 build is ignored.
- Nothing else depended on the notice: the revoke, the capabilities gate and the busy retry work as before.

## (c) Anything new in these commits?

- L2 (commit comparison for split-tunnel starts) and N1 (non-atomic save check): yes, both from 8d233e25.
- `resumableSession`: I walked the ways a refused outside start can reach a hold. Each one passes one of the two clearing lines first:
  - with or without a delivered `.connecting`;
  - online or offline;
  - after the owner used and disconnected the profile earlier in the same run.
- A session that actually connected is signable, which matches how a live connected session was always treated.
- A hold re-entered at launch is never signed. That is a small loss of function (Pause in a restart hold right after a relaunch doesn't reconnect), and it is documented.
- Launch spend of the pause value: it is started only when nothing is paused, and every `pause()` ends it first, so it can't coexist with a live pause. Bounded at five retries.
- Agent: with nothing paused it now needs one successful keychain delete before it unregisters. If the delete keeps failing it runs each minute until the next GUI launch unregisters it. Harmless.
- The "off" seal on `.unavailable`: bounded as before (10 retries per run, then at each `load()`). A forged "off" still only turns Auto-Connect off.
- Nothing else found.

## Test hosts and the real keychain

No other test can reach the real keychain at HEAD.

- The only route in app code was the default argument `keychain: any SecretItemStore = DataProtectionKeychain()` of `HeadlessResume.perform` (`App/Headless/HeadlessResume.swift:82`). All 34 test calls now pass a keychain.
- No test file names `DataProtectionKeychain`, `LoginKeychainReader` or `liveBackends`. The test harness builds `Backends` with an `InMemoryKeychain`, and `Backends.keychain` has no default.
- The host app under XCTest uses preview backends (in-memory keychain) and returns before `env.start()`.
- `RequirementTests` (the UnitRelease plan) is not hosted. `LockPlusTests` can't build in Release (`ENABLE_TESTABILITY = NO`), so the Release host, which would run live, is not reachable from tests.
- Package tests pass a fake backend wherever they build `SystemKeychainSecretStore` or `TunnelSecretStore.make`.

What remains is structural (N3):
- The default argument is still there, so the next test that omits `keychain:` reaches the real one again.
- The reported run failed only because the host was unsigned. I did not check whether a development-signed Debug host carries the access group; if it does, the same call would have deleted the installed app's pause value.
- Make the parameter required.
- The same pattern exists for the login keychain in `SystemKeychainSecretStore.init(backend: = SecItemBackend())` and `Tunnel/SecretStorePrefix.swift:14`.
