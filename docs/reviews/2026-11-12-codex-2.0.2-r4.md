**1. HIGH — Provisioning can still fail a kill-switch replay during stale-provider teardown. Remaining R3 #1; 2.0.2 interaction with the pre-existing guard.**

[TunnelController.swift:400](native/Packages/TunnelEngine/Sources/TunnelEngine/Controller/TunnelController.swift:400), [TunnelController.swift:1502](native/Packages/TunnelEngine/Sources/TunnelEngine/Controller/TunnelController.swift:1502), [TunnelController.swift:1965](native/Packages/TunnelEngine/Sources/TunnelEngine/Controller/TunnelController.swift:1965).

NE’s authorised replay encounters the previous provider’s stopped/freed lease. `start` calls `await stop(.superseded)`: this removes the old session before awaiting its adapter teardown. The replay remains in `guardedStarts`, without a reservation.

If background validation provisions revision 2 during that teardown, `payloadCommitted` invalidates the revision-1 replay. When teardown finishes, the guard throws `startCancelled`. There is now no incumbent session protecting the Mac; the legitimate kill-switch restart has failed.

The comment asserting that every guarded start waits beside a protective live session is false for this branch.

**Fix:** Preserve authorised kill-switch replays throughout the guard and stale-provider teardown, allowing them to adopt the committed payload.

**Regression needed:** Connected revision 1 → old lease becomes stale → replay waits on a deliberately slow adapter stop → provision revision 2 → release stop → replay succeeds. The new tests begin provisioning after the replay has already created its adapter, missing this interval.

**2. HIGH — A delayed stop notice can revoke a newer session’s restart permission. New-in-round-4; introduced by FIX3.**

[ProfilesStore.swift:819](native/App/Stores/ProfilesStore.swift:819), [TunnelController.swift:1402](native/Packages/TunnelEngine/Sources/TunnelEngine/Controller/TunnelController.swift:1402).

A user stops session A, but its notice encounters a busy extension. A subsequent authorised on-demand session B of the same profile connects. Its rules are later withdrawn, and a network interruption ends B without a user stop. A’s delayed notice then arrives during B’s restart gap.

`userStopped` identifies only the owner and profile. With no current session, it deletes **B’s** authorisation and marks the profile user-cleared. B’s legitimate NE replay consequently receives 225 and leaves the Mac open.

This is the documented risk 30(1), and it violates the requested stop condition. Removing an ID in `userStarted` also cannot retract a notice already captured by `revokeOnce`. Furthermore, a successful first page followed by a failed later page retains the stop notice for another delivery.

**Fix:** Bind notices to the stopped admission/session generation and conditionally revoke that generation. Acknowledge stop delivery independently of keep-set pagination.

**Regression needed:** Undelivered stop A → authorised session B → non-user end of B → deliver A’s notice → B’s replay succeeds. The existing cancellation test checks the pending set, not this controller sequence.

**3. MEDIUM — Cancellation notices disappear before capability discovery or across app exit. Remaining R3 #3; incomplete 2.0.2 fix.**

[ProfilesStore.swift:843](native/App/Stores/ProfilesStore.swift:843), [ProfilesStore.swift:848](native/App/Stores/ProfilesStore.swift:848), [AppEnvironment.swift:328](native/App/AppEnvironment.swift:328).

`userStopped` discards the notice when extension capabilities are still unknown. Connection recovery is restored before extension activation/hello completes, so Cancel during that interval can take this path.

Even after capability discovery, undelivered notices exist only in `pendingUserStops`, an in-memory set. Cancel an already-down unattended kill-switch session while the extension is busy, then quit before the retry: relaunch loses the notice. Passive reconciliation intentionally preserves its kill-switch authorisation.

Another local user can subsequently start the cancelled profile without options, using the retained unattended permission and saved credentials.

**Fix:** Queue stops before capability discovery and persist session-scoped cancellation intent in protected storage until acknowledged or superseded by a genuine new owner start.

**Regression needed:** Both Cancel-before-hello → successful hello, and busy Cancel → quit/relaunch → successful delivery. Assert an outside start receives 225. The current retry test covers neither lifecycle.

**4. MEDIUM — Removing the pause’s profile ID preserves a replayable one-time value. Remaining FIX3/Fable L2; pre-existing in 2.0.2.**

[ConnectionStore.swift:2353](native/App/Stores/ConnectionStore.swift:2353), [ConnectionStore.swift:2384](native/App/Stores/ConnectionStore.swift:2384), [HeadlessResume.swift:118](native/App/Headless/HeadlessResume.swift:118).

Same-user malware copies a genuine pause record and its expiry, then replaces `pausedState.profileID` with `null` before expiry. Both GUI and headless paths finish the pause and clear its settings without consuming `.pause`: consumption requires either a known target or a non-nil unknown profile ID.

Restoring the genuine record within its seven-day freshness window therefore passes authentication. Launching LockPlus makes the signed app arm and start the saved profile again, although the earlier pause already ended.

**Fix:** Consume the pause value whenever a pause ends, including absent state or absent profile ID, while preserving explicitly retryable outcomes.

**Regression needed:** Genuine pause → nil profile ID at expiry → pause ends → restore genuine record → no arm/start, in both GUI and headless paths. The existing failed-check test substitutes another non-nil profile, so it misses this branch.
