## Findings, most severe first (all LOW)

**1. L-4's launch guard drops a hold that was entered DURING a pause, whose stop was never issued (regression).** `resumeNetworkRestartAtLaunch` ConnectionStore.swift:516 requires `pausedUntil == nil`. With `pause()` now clearing the record in its own write (:1522), a record that coexists with a pause can only mean the refusal happened *after* the pause began (a Connect during the pause, refused for no network; `pause()` only clears what existed at its start) or an older file. Scenario: paused → user Connects X → refused → `.awaitingNetworkRestart(X)` recorded → relaunch before the network returns → record dropped, no `stopVPNTunnel` → NE's restart of X is still pending; at pause end `resume()` → `connect(target ≠ X)` runs its pause/prepare saves inside X's pending restart, or with `target == nil` `restoreIfIdle` turns on-demand back on beside it (the 200011 failure mode, now without the GUI's knowledge). Before this commit the hold was re-entered and `connect(target)` stopped X first (`held`). Fix: delete the `pausedUntil == nil` condition (the same-write clear already covers the race the guard was for; a stale older-file record costs at most network-return + 10 s and is dropped when the manager is live/gone/has rules). Test `aLaunchDuringAPauseDropsTheRecord` (NoNetworkRestartTests.swift:484-496) writes `pausedUntil` *after* `refused(w)`, a state `pause()` can no longer produce, and asserts the wrong outcome for the state it can; replace with "refusal during a pause, relaunch → hold re-entered; resume stops X then starts the target".

**2. The network-return start has no one-start-at-a-time guard.** `applyNetworkToHolds` :489-502 → `beginStart` skips `connect()`'s `pending.allSatisfy` guard (:818). L-1 now creates entries for sessions started elsewhere, so this is reachable: offline, Connect X (`.waitingForNetwork`), user starts kill-switch/no-rules Y in System Settings → refused → Y `.awaitingNetworkRestart`; network returns → Y's fallback armed, X's start after `endpointPushSettle` (2 s). If NE's restart of Y has landed (`.connecting` at 1.1-1.3 s, the usual case) `beginStart` switches out of it: fine. If it lags the settle, `startNow(X)` runs X's `prepareForStart` and pause saves inside Y's pending NE restart (R1: "nothing may be saved before it"; U13 breaks that restart, fail-closed, X proceeds; a later `.connecting` of Y meets F6). Fix: in the Task, `guard pending.allSatisfy({ $0.key == id })` else keep `.waitingForNetwork` and re-run `applyNetworkToHolds()` from `clearPending` when the other entry ends (or drop with the L-2 note). No test covers a second entry at network return.

**3. L-1's hedged hold for a non-current profile: Cancel targets the wrong profile for the fetch window.** `holdForSystemRestart` (:382-386) doesn't touch `currentID`; our own issued start set it in `beginStart`, but the new `unwatchedEnd` path (:319-323) holds X while `currentID` stays Y. UIBinder.swift:190 renders the hold row ("Checking whether X starts…", Cancel per DerivedState.swift:223) on Y's hero; Cancel → `disconnect()` (:1409) stops Y (`userStops[Y]`, `managers.stop(Y)` on an idle session) and leaves X's hold alone until the fetch (≤ 10 s) and, if code 2 isn't read, the 10 s fallback. `holdForNetworkRestart` (:437) does set `currentID` once code 2 is read, so Cancel works from then. Fix: in the `unwatchedEnd` branch set `currentID = id` when `statuses.allSatisfy { !$0.value.isActive }` (as :437), or make Cancel act on `startHold.profile` for `mayRestart`/`startEndedEarly` holds. `aSystemSettingsRefusalForNoNetworkIsHeldToo` doesn't assert `currentID`/Cancel.

**4. L-1 misfire on normal ends of never-seen-active sessions (bounded).** The launch-mid-session case asked about is safe: `start()` :217-221 puts the active current profile into `sawActive`, so a later System Settings stop goes through `observedDisconnect` as before. Not covered: a session already `.disconnecting` at launch, or a second concurrent session (only `currentID` is marked), of an own kill-switch/no-rules profile. Its `.disconnected` now enters the hedged `.startEndedEarly` hold ("The start ended early", wrong copy) for the fetch + ≤ 10 s, with the restore held meanwhile; before the commit it restored at once. Also `mayBeRestartedByNE` reads a stale `sessionKillSwitch[id]` from the profile's previous session (:1262; never cleared for a known manager), so a profile whose kill switch was turned off since can still get the 22 s teardown entry + 10 s hold. Bounded, Cancel offered (modulo 3); accept, or narrow `holdTeardown`'s new arm to `statuses[id]` having been `.disconnected`/nil before the `.disconnecting` and read `managerKillSwitch` for a session we never saw.

**5. Nit, `dropWaiter` is broader than L-2 and its copy can be wrong.** :332 drops the waiter whenever `pending[old] != nil`, which includes the plain fetch entry of a session NE will NOT restart (on-demand rules/no kill switch), reachable when the Connect came while `managers.status(old) == .disconnecting` was ahead of the handled event (:856-868). The note says "macOS may restart Y" regardless; the click vanishes from the hero (`.readingDisconnect` shows no row, StateInputs.swift:136) and Connect is re-offered only after the fetch (≤ 15 s). Fix: drop only when `mayBeRestartedByNE(old)` (else `startNow` as before), or word the note generically. No test exercises `dropWaiter` at all.

**6. Nit.** `observedDisconnect` :689-692 sets `crashed = true` before `holdForNetworkRestart` can return false (hold ended during the write); `noNetwork` then false, `mapped` set → `.stoppedUnexpectedly` fires (:731) for a refusal whose hold was already over. Set `crashed = noNetwork`.

**7. Nit.** `checkNoNetworkRefusal` never sets `observedError`, so after our own refusal + fallback with no restart the hero shows row 15 "Not protected" with no reason; the new row 14 copy is reached only via the `sawActive` path.

**8. Nit, pre-existing.** `pause()` :1504-1506 reads `held`/`live` before its durable write; a hold ended by NE's restart landing during the write is neither stopped (`stopNetworkRestart` guard :473) nor in `live`, so X runs through the pause with others' on-demand off; `pausedState.profileID == X` so the resume is consistent.

Other checks asked for, no finding: own reconnect (N1b) is exempt from the drop (`target != id`) and starts at `.disconnected` after a user stop or over a teardown entry; the own-Connect-during-our-refusal-teardown case is replaced by the hold as before (UI holds it, pre-existing). Delete of the held profile: `stopAsUser` :596-600 stops synchronously, forgets the record, restores, and `stopAndWait` returns at once (test covers; restore vs. removal are saves of different idle managers). Launch order `resumeNetworkRestartAtLaunch` → `resumePauseAtLaunch` → `restoreIfIdle` is right (an expired pause's `connect(target)` sees the hold and stops X first); only the guard (1) is wrong.
