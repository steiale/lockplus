## Findings and nits

- **#1 closed.** `resumeNetworkRestartAtLaunch` (ConnectionStore.swift:543) no longer needs `pausedUntil == nil`. With `pause()` clearing the record in its own write (:1550) a surviving record during a pause can only be a refusal during the pause (or an older file, which costs ≤ network-return + 10 s). Launch order is right: hold armed → `resumePauseAtLaunch` → `resume()` → `connect(target)` sees `held` (pending.count == 1) and stops X before `beginStart`; `target == X` → own hold ignores it with the "macOS connects it" note; `target == nil` → `restoreIfIdle` is busy, record stays until the hold ends. Test replaced with the reachable state.
- **#2 closed.** `applyNetworkToHolds` (:516) keeps `.waitingForNetwork` while any other entry exists; `clearPending` (:1340) re-runs it when a non-waiting entry ends. Every entry removal goes through `clearPending` (`pending[id] = nil` only at :1337; `arm` replaces, doesn't remove), so nothing is stranded. No loop: `applyNetworkToHolds` only spawns Tasks / re-arms `.awaitingNetworkRestart` (and `available == fallbackArmed` already holds after each path report, so no timer reset); stale Tasks die on the token check (a `startNow` → `waitForNetwork` re-arm changes the token too). No start inside another entry: the guard runs after the settle, then `beginStart` runs synchronously. Starvation bounded by the blocker's own timers (10 s fallback, 22 s teardown, 30 s start).
- **#3 closed** at :323 (`currentID = id` when nothing is active) — Cancel of the unwatched `.startEndedEarly` hold stops that profile (test). Another profile's Connect is held during the fetch window (`connectHold` → `.startEndedEarly`), and `connect()`'s guard ignores it, so the current profile can't change under the hold except by Cancel/delete (delete: `stopAsUser` → `stop`, `dropVanished` → `sessionEnded` ends the entry). Residual: regression 1 below.
- **#4 closed.** `holdTeardown` (:365-373) arms the unwatched teardown only for `previous == nil || .disconnected`, own profile, `managerKillSwitch`, no on-demand; `sessionKillSwitch[id] = true` keeps `mayBeRestartedByNE` consistent at the `.disconnected`. The measured System Settings refusal is always held: `start()` seeds `statuses` with `.disconnected` for every manager (:216), and before `start()` `previous` is nil. Our own issued refusal is held on the `issuedStartEnded` path regardless of `previous`. Residual: nit 2.
- **Nit 5 closed** (:337, `mayBeRestartedByNE(id)` added). Residual: regression 2.

## Regressions / residuals, most severe first (all LOW)

**1. LOW (side effect of #3): hero profile and 12a row disagree while a `.waitingForNetwork` entry coexists with the unwatched hold.** Scenario: offline, Connect Y (`.waitingForNetwork`, `currentID = Y`), user starts kill-switch X in System Settings → refused → :323 retargets `currentID = X`; `startHold` (:1257) picks `pending.first(where: phase != .awaitingRestart)` = Y's wait, so X's hero shows "Waiting for a network to connect Y…" for the fetch window; once code 2 is read (X `.awaitingNetworkRestart`) the pick is dictionary order, either row. Cancel → `disconnect()` on X: `cancelPendingStarts` drops Y's Connect silently (no `dropWaiter`-style note) and stops X. Before this commit the hero stayed Y until `holdForNetworkRestart` (:448, pre-existing) retargeted. Fix: make `startHold` deterministic and hero-consistent — prefer `pending[currentID]` when it is not a bare `.awaitingRestart`; and note the dropped wait in `disconnect()` when a `.waitingForNetwork` entry of another profile is cancelled (or restrict `cancelPendingStarts` there to `currentID`). No test has two entries with the current profile ≠ the waiting one.

**2. LOW (re-opened by nit 5's narrowing): a waiter started beside a non-restartable session's fetch entry can meet the app's own PF-52 crash restart.** :337 now runs `startNow(T)` when `pending[Y]` is Y's fetch entry and Y has on-demand rules (reachable only when T's Connect landed in the ms window where `managers.status(Y) == .disconnecting` was ahead of the event, `stoppingOther` :892-895, as `statusAheadOfItsEvent` models). If the fetch reads a fresh `pluginFailed` crash, `restartAfterCrashIfNeeded` (:1734) decides `.restart` after the 1.5 s grace unless T's `pauseOtherOnDemand` has already turned Y's on-demand off; `crashDecision`'s `switching` (:1780) reads `switchTarget` = a `.waitingForStop` entry, and T is `.starting` now, so it doesn't see it → `managers.start(Y)` beside T's pending start (F6 then switches out of Y: fail-closed, messy). At aad7527 the waiter was dropped. Fix: count any other pending start as switching in `crashDecision` (`switchTarget != nil || pending.contains { $0.key != id && $0.value.isStarting }`), or keep dropping whenever `pending[old] != nil` and word the note generically. The new test's second half uses a session with no entry at all (Split, unwatched), so the `pending != nil && !mayBeRestartedByNE` branch isn't exercised.

**3. Nit (#4): `previous == .disconnected` excludes `.invalid`.** :251-256 stores `.invalid` into `statuses` for a known manager after `.disconnecting`; `sessionEnded` nils it only when the manager is unknown (:571-580), and nothing re-syncs `statuses` from the managers after launch. A later System Settings refusal of that profile is then not held at `.disconnecting`; its `.disconnected` has no teardown entry → no hold → restore beside NE's restart. Our own issued refusal is unaffected (`issuedStartEnded` path). Fix: `previous == nil || previous?.isLive == false`.

**4. Nit (nit 8): `pausedState.profileID`/`restore` are computed before the write (:1532-1543).** A hold that began during the write is stopped (`heldNow`) but not recorded as the profile to reconnect; the user's Connect is lost at the pause's end. Compute `active` from `liveNow ?? heldNow` inside the closure (the write already runs on the ordered queue after the hold's own write).

**5. Nit (#4, accepted narrowing, for the record):** a second active own session at launch that isn't `currentID` is never in `sawActive` (:219-223), so its teardown is no longer hedged. Putting every active manager into `sawActive` at `start()` would make the narrowing cost-free.

Other checks: `stopAsUser`/delete, `dropVanished`, `cancelPendingStarts` and `pause()` all go through `clearPending`, so the #2 re-run fires on every end path; iteration in `cancelPendingStarts`/`dropVanished` is over copies, so the re-run's `arm`s are safe. `holdTeardown`'s `managerKillSwitch` read is the loaded config's flags, as asked. Headless resume unchanged and still consistent with the record surviving a pause.
