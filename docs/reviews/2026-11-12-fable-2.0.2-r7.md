## LOW

### L1. Pause no longer reconnects the owner's own session when it is pressed while macOS's restart of that session is `.connecting` (new in 141fe80c; from reading, not run)

- `App/Stores/ConnectionStore.swift:364`: a new attempt that this run did not issue is removed from `resumableSession`. NE's own restart of a session the app watched is such an attempt (`issued` is false in `.awaitingRestart` and `.awaitingNetworkRestart`).
- Until this round that did not matter for a live session: Pause signed any live session. Now `signableLive` (`:639`) asks the set, so the restart is unsigned until it reaches `.connected`.
- Two ordinary sequences:
  1. Connect P (kill switch), connected; the tunnel process crashes; NE restarts it and P is `.connecting`; Pause.
  2. Connect P offline (refused, network-restart hold); the network returns; NE restarts P, `.connecting`; Pause.
- In both, a Pause one moment earlier (in the gap or the hold) is signed and reconnects. Once `.connecting` shows, the pause stops P with `pausedState.profileID == nil`, and its end arms and starts nothing. No note says so.
- `.connecting` can last a long time here: a before-Connected hold in the extension keeps NE at `.connecting`. "The VPN is stuck reconnecting and blocks traffic" is a likely reason to press Pause.
- A profile with Auto-Connect rules is not affected (its rules come back at the pause's end and reconnect it). A kill-switch profile without rules stays down after the pause.
- LOW: no attacker, and the result is a missing reconnect, visible in the hero and the menu bar. But it is silent, it is a regression, and the CHANGELOG line "Pausing while macOS is about to restart a kill-switch session… reconnects the profile when the pause ends" reads as covering it.
- The existing `aRestartDuringThePausesWriteIsStoppedAndReconnectedLater` still passes only because the hold was signed before the write.

Fix: in `handle`, before `statuses[id] = status`, take `let wasSignableHold = signableHold == id`, and make line 364 `if !issued, !wasSignableHold { resumableSession.remove(id) }`.
- This signs nothing that a Pause an instant earlier would not have signed, so round 6's L1 stays closed. Its sequences (no hold, or a hold that is not signable) still clear the set.
- Tests: `refused(w)`, `emit(P, .connecting)`, Pause → signed and started at the end; the same after `crashed(h, p.id)`.
- If it is not fixed: say so in D10.10-4 and the CHANGELOG line, and add the E2E row below as a known limitation.

### L2. The owed flag is reset by writing back an older copy of settings.json (residual of Codex r6 #3)

- `pauseValueOwed` lives in unsigned `settings.json`. `anExhaustedSpendStaysOwedAndARestoredPauseNeverResumes` restores the genuine record by editing two fields, which keeps the flag.
- An attacker who copied `settings.json` at step 1 and writes that whole copy back restores `pausedState`, `pausedUntil` and `pauseValueOwed: false` in one go, without knowing the flag exists. The GUI's end of that pause, or the agent if it is registered, then checks the record against the surviving value, and it holds: P is armed and started.
- So the fix closes a quit or crash while the value is owed, and a surgical edit. It does not close Codex's sequence in the form most code would use.
- Clearing or forging the flag does no other harm:
  - Cleared: back to round 5's behaviour, nothing worse.
  - Forged `true` beside a genuine pause: that pause's value is spent first and its end reconnects nothing. Same-user code can already get that by damaging the record.
  - Forged `true` with nothing paused: one successful delete of a value nobody needs, and an agent that is kept until then.
- LOW, not MEDIUM, because the precondition is a data-protection keychain whose delete fails through a whole GUI run (six tries, no later `load()` or wake). I know no way for same-user code to cause that. The gain is one unattended start of the owner's own verified profile, within 7 days of the pause's end (`ResumeIntent.maxAge`).
- There is no full cure without storage the same user can't write. DESIGN says the flag is unauthenticated (D10.10-3, risk 31 (b)). The CHANGELOG line ("keeps trying… before any pause record is acted on again") claims more than holds.
- Suggested: correct that line, and add the whole-file variant as a test that documents the residual.

## NIT

- **N1. The agent does not record a failed spend before `.networkRestartPending`.** `App/Headless/HeadlessResume.swift:139-149` spends when the record does not hold or names no profile; `:157` can then return with the pause kept and `owedNow` unsaved (also a watchdog exit before the final write). FIX6 says the agent "records every failed spend". One `saveOwed()` before that return.
- **N2. At the launch where the debt arises, the agent is already unregistered.** `AppEnvironment.swift:328-329` runs `reconcileResumeAgent()` right after `connection.start()`, before the launch's spend has failed, so `.unregister where s.pauseValueOwed` does not apply yet. The test calls reconcile after the spend. Harmless (an agent that is gone can't act on a record), but "the agent stays registered" holds only for a debt from a pause's end or from an earlier run.
- **N3. Extending a pause carries a record without spending an owed value first.** `ConnectionStore.swift:2272-2283`: with the value owed and the genuine record written back, the owner's own Pause (extend) finds the old record valid, carries its profile and seals it afresh. It needs the owner's click and is covered by L2's attacker anyway. Fix: carry nothing while `pauseValueOwed`.
- **N4. Test gap (mutation H3 survives).** An after-Connected prompt built without `revision:` passes the suite: no test expects an after-Connected Save at the current revision to be written. The effect would be a Save that is silently dropped, never a wrong write.
- **N5. One default route to the real keychains is left.** `AppEnvironment.init(mode: AppMode = .detect())` (`App/AppEnvironment.swift:177`) builds live backends (data-protection keychain, login keychain reader, the standard data directory). No test calls it today; `AppDelegate` passes `.preview` under XCTest. Same class as round 6's N3.
- **N6. Outside the diff, not checked further.** `EngineServiceBackend.provision` checks the stored revision and then writes the payload in separate store calls, so two concurrent provisions of one profile could interleave. I did not check whether the app can issue two at once.

## The points you asked about

- **Conditional credential put.**
  - Both real stores do `entry(.payload)` and `put(.credential)` as synchronous actor-isolated calls with no `await` between them, so no other store call can run in between.
  - It is an actor turn, not a keychain transaction. That is enough because the extension is the only writer and builds one store (`TunnelEngineAssembly`, `private init`).
  - The fake waits before its check, then checks and writes without suspending, so it models the same thing.
  - The container store reads the revision from the file's unauthenticated header, as `entry` always did. Only root can write there.
- **`answerRevision` binding.**
  - Set only where the stash is set; cleared at every place the stash is cleared.
  - An attempt that fails before the hand-over keeps the stash and its revision, and the next load compares again.
  - A prepared answer has none, as documented; `profileProvisioned` drops prepared answers.
- **`pauseValueOwed`.** See L2 and N1–N3. The spend chain can't run beside a pause that is being made: `pause()` cancels and awaits it before it seals, and each seal clears the debt in the same durable write as the record.
- **`resumableSession` filter.** One legitimate Pause no longer resumes: L1. Two more were changed on purpose and are small:
  - A session found `.connecting` at launch.
  - The owner's own start from System Settings while it is still `.connecting`.
- **Split vs kill-switch comparison.** As intended. A split start ends on any commit above its NE configuration's revision; a kill-switch start restarts its attempt only for a commit above the revision it loaded.
- **Required keychain parameters.** The three signatures have no default; the two production call sites pass the real ones.
