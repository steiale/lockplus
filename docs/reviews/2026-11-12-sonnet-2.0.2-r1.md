## HIGH

None. No single defect found that breaks a core invariant on its own. The two items below that come closest are ranked MEDIUM only because both depend on an NE behaviour the plan already lists as unverified (E2E S6) or a short window.

## MEDIUM

**M1. A timeout of the validator is persisted as a permanent refusal.** `native/App/Services/ServiceProfileValidator.swift:23-25` maps both `.profileCheckCrashed` and `.timeout` to `.rejected(category: "check crashed")`. `ProfilesStore.verifyPending` (`ProfilesStore.swift:896-901`) writes that into the profile's import report, and `alreadyRejected` (`:884`) then excludes the profile from every later re-verify (that is the point of the L7 guard). Result: a good profile that merely hit the 8 s client timeout once (cold first launch of the XPC service on a loaded Mac, first launch after an update, 27.x sandbox warm-up) is permanently "not supported", with no retry and no user action available. The integrator already flagged this. Fix: only `.profileCheckCrashed` becomes `.rejected`/`.checkCrashed`; `.timeout` rethrows (-> `notChecked`, "Not yet verified", retried at launch and after every hello, copy already says "It tries again automatically"). A genuinely hanging file then re-hangs the service once per launch/hello; bound that with a per-profile in-memory attempt counter in `verifyPending` (e.g. give up after 2 per run) rather than persisting a verdict. Also add a test: timeout in `verifyPending` leaves `engineVerified == false` and no report item (the existing `aRejectedProfileIsNotRecheckedOnEveryHello` only covers the crash path).

**M2. Editing a connected profile clears the replay authorisation of the still-running session.** `TunnelController.swift:1772` (`profileProvisioned` -> `clearAuthorisation(key)`) runs on every higher-revision provision, but a provision does not end a running (Connected) session (`payloadCommitted` only ends a *waiting* start, `:1785`). If the user saves an edit of a connected profile without reconnecting (the "Save" path of the "Save and reconnect?" prompt), the session keeps running on the old payload with its authorisation gone; a provider crash before the next app-armed start makes NE replay the old nonce -> 225 -> for a kill-switch profile without on-demand that is the "left open" outcome the plan names as worst case (PLAN §3.7). Window is narrow and needs a crash, but it is a deterministic hole, not a race. The test `higherRevisionClearsAuthorisationButASameRevisionRetryKeepsIt` asserts the clearing, not the consequence. Fix: in `profileProvisioned`, if `session?.key == key` (a live session), keep the authorisation (or re-key it to the new revision) and let the user stop / removal / the next armed start replace it; clear only when no session exists. Add a test: armed + connected, higher provision, crash, NE replay with the old nonce is honoured. Also verify this row in E2E S-"Edit a connected kill-switch profile" with a `kill -9` between edit and reconnect.

**M3. Self-test can read "Blocked, nothing leaves outside the tunnel" (pass glyph) without proof.** `ConnectionSelfTest.swift:~118-121` classifies any non-timeout failure of the IPv6 fetch as `.blocked` when full tunnel + (kill switch or blockIPv6) + tunnel has no IPv6. In `ProbeSession.handle`, `.waiting(e)` and `.failed(e)` both finish immediately with `timedOut == false` (`:~300-306`). These states also arise from causes that prove nothing about the path: a DNS failure for the AAAA record (tunnel resolver filters AAAA / returns NODATA), a transient "no path yet" right after connect or during reassert, a TLS failure. The comment says "Only a prompt refusal counts as blocked", the code accepts every prompt failure. Violates the plan's own rule "inconclusive never green". Fix: set `blocked` only when the NWError is a POSIX `ENETUNREACH`/`EHOSTUNREACH`/`ENETDOWN`/`ECONNREFUSED` (record the errno in `ProbeFetch`), treat `.dns` and `.tls` errors as `unreachable`. Same consideration for v4: a `.waiting` should not end the probe early on a transient path (let the 6 s timer decide unless the error is a definite POSIX unreachable). Add rows to the `classify` table for DNS-failure and TLS-failure -> `.unreachable`.

## LOW

**L1. Stale user-visible text in Problems.** `ProfilesStore.swift:902`: `note("\(p.name) isn't supported by the tunnel component: \(category)")`. 2.0.2 moved this check out of the tunnel component, and for the crashed case the message becomes "...isn't supported by the tunnel component: check crashed". Also not localised (pre-existing pattern for `note(...)` but this one now describes the wrong component). Fix: localised "LockPlus's file checker rejected %@: %@" or reuse `.checkCrashed` text; for crashed: "LockPlus couldn't check %@ safely." Related stale internal strings: `ConnectionStore.swift:1234` detail "not yet verified by the tunnel component"; `ProfilesStore.swift:841` unchanged and correct.

**L2. Stringly-typed round trip for the crash verdict.** `ServiceProfileValidator.crashedCategory = "check crashed"` is encoded into `.rejected(category:)`, then decoded back by string comparison in two places (`validateWithService` `ServiceProfileValidator.swift:41`, `ProfilesStore.swift:899`). A real openvpn3 category equal to that string (unlikely) or a rename in one place silently changes behaviour. Fix: add `OVPNEngineEvaluation.Verdict.checkCrashed` (or a `crashed: Bool` field) and switch on it in both places; delete the string constant.

**L3. Wrong issue kind for over-long but safe zip names, and silent issue truncation.** `ArchiveReplyBuilder.swift:19-22`: an entry whose name is 256-1024 bytes (the reader's `ZipCaps.maxNameBytes` default is 1024, the wire's `maxNameBytes` is 255) is reported as `.unsafePath`, so the user is told "has an unsafe path". The `entries.count < maxEntries` and `bytes.count <= maxEntryBytes` arms are unreachable (reader caps 500 entries and 1 MiB first) and would also say "unsafe path". `:31` `removeSubrange(maxIssues...)` silently drops issues beyond 500 while `SectionModels.swift:200` promises "never silent truncation". Fix: pass `maxNameBytes: ReadArchiveReply.maxNameBytes` in `ArchiveReplyBuilder.caps` (reader then produces the right issue), drop the dead guards or make them `precondition`s, and append one synthetic "and N more skipped" issue (or a new `.moreIssues(Int)`) on truncation.

**L4. `ZipCaps()` defaults still carry the 2.0.1 limits.** `LPModel/ZipModel.swift`: `maxEntryBytes = 10 << 20`, `maxTotalBytes = 100 << 20`, `maxNameBytes = 1024`. The shipped values (1 MiB, 64 MiB, 255) exist only as an override in `ArchiveReplyBuilder`. Anything constructing `ZipCaps()` (tests, `ReadArchiveRequest.maxArchiveBytes`, the fuzz target) tests the old caps. Fix: make the defaults the shipped values and delete the override.

**L5. Client timeout of `readArchive` (30 s) is unreachable.** `ValidatorWire.swift:93`: service watchdog is 10 s (`ValidatorLimits.watchdog`), so a slow archive is killed at 10 s, surfaces as an interruption, is retried once (another 10 s) and ends as `.profileCheckCrashed` after ~20 s, never as `.timeout`. Either raise the watchdog for `readArchive` (e.g. 25 s, the inflate of 64 MiB is nowhere near it, but a slow CPU under load might be) or drop the client timeout to 12 s and say so in DESIGN 10.4 (which currently documents only the 8 s vs 10 s pair for evaluate).

**L6. Overstated sandbox claim in CHANGELOG.** `CHANGELOG.md` 2.0.2 "Changed": "with no network or file access". The service has the App Sandbox default (read access to system locations, its own empty container); DESIGN 10.4 correctly says "no files beyond its empty container". Say "no network access and no access to your files".

**L7. CHANGELOG claim vs Info.plist rank.** "LockPlus becomes the default app for `.ovpn`": `LSHandlerRank = Default` only registers a candidate; if Tunnelblick/Viscosity/OpenVPN Connect is installed it is not the default. Reword: "LockPlus is offered as the default app for `.ovpn`".

**L8. Persisted authorisation cap (256) is in neither DESIGN nor CHANGELOG.** `TunnelStateStore.swift:38` `maxAuthorisedStarts = 256`, eviction by oldest `at` in `recordAuthorisation` (`TunnelController.swift:~1315`). The Phase 2 report says "documented as code"; DESIGN 10.4 documents the 15 s TTL and the 8-per-uid arm cap but not this. Note too that evicting the oldest silently makes that profile's NE replay fail (225) on a crash: 256 profiles is unrealistic for one machine, so only the doc is missing.

**L9. `.waiting` finishing the probe at once** (see M3) also affects v4 right after Connected: the self-test button is enabled as soon as `connectedProfileID != nil`, and the first press within ~1 s of connect can produce "Couldn't reach the test host" on a path that is still settling. Fix: require the 2.0.1 settle used for the DNS verifier (`DNSVerifier.delayAfterConnect`) before enabling, or retry `.waiting` once after 500 ms.

**L10. Weak / non-testing tests.**
- `OpenDocumentRouterTests.queueIsBounded`: 50 x 100 identical URLs dedupe to 100 paths, so the result (`tooMany`) is identical with an unbounded queue; the 1000-URL bound is never exercised. Use 50 x 100 *distinct* URLs and assert `pending` never exceeds `maxQueuedURLs` (needs a read-only accessor) or assert memory-bound behaviour through the outcome (e.g. 1000 distinct + 1 -> still `tooMany`, and a flush afterwards is empty).
- `assert-test-count.sh` floors (`Unit 789`) count skipped tests (`totalTestCount`), so 40 newly skipped tests would still pass. Add `skippedTests <= 40` (or assert `passed >= 749`).
- `StartAuthorisationTests.higherRevision...` uses `payloadCommitted` for the "same-revision retry" case and so never exercises the `higher` guard in `EngineServiceBackend.provision` (`:159`); add a backend-level test (same-revision provision keeps the authorisation).

**L11. Unverified assumptions that decide the worst outcome.** The kill-switch replay path (S6/S8) depends on NE replaying `lp.startNonce` in the persisted options. Not testable in unit tests; keep as hard stop in E2E-8 (plan already lists it). Suggest one extra row: kill-switch profile started *by Auto-Connect* (no nonce at all) then `kill -9` (should be `.unattended`), to prove on-demand replay without a nonce.

## German strings (`native/App/UI/Localizable.xcstrings`, all new/changed keys read)

All new keys have a `translated` DE value; no placeholder mismatches (`%1$@`/`%2$@` used where arguments are reordered or repeated: `'%@: %@'`, `Through the tunnel (%@, from %@)`). Natural du-form throughout ("Verbinde dich zuerst", "Versuche es erneut", "Öffne höchstens 20 Dateien"). Meaning matches EN, including the corrected "Blockiert, nichts geht am Tunnel vorbei". Points to fix:

1. `LockPlus hasn't checked this profile ... It tries again automatically; until then the profile can't connect.` -> DE "Es versucht es automatisch erneut" is ambiguous (Es = LockPlus or Profil?) and "es ... es". Better: "LockPlus hat dieses Profil noch nicht mit seiner OpenVPN-Engine geprüft. LockPlus versucht es automatisch erneut; bis dahin kann sich das Profil nicht verbinden."
2. Terminology: "prüfen" (new check strings, `Checking %@…`, `couldn't be checked safely`) vs "überprüfen" (`Couldn't verify DNS`, `could not be fully verified`). Defensible (check vs verify) but the integrator's "verify = überprüfen" rule also leaves "Prüft, ob IPv4, IPv6 und DNS den Tunnel nutzen." next to "konnte nicht vollständig überprüft werden". Acceptable; if you want one term, use "prüfen" everywhere in the self-test section.
3. `%@ unpacks to more than 64 MB` -> "%@ ist entpackt größer als 64 MB" is clumsy; "%@ ist entpackt größer als 64 MB und kann nicht importiert werden." is understandable but "Entpackt ist %@ größer als 64 MB und kann nicht importiert werden." or "Der Inhalt von %@ ist größer als 64 MB und kann nicht importiert werden." reads better.
4. `Reconnecting…` -> "Neuverbindung…" is pre-existing (not new), but sits beside "Verbindung wird hergestellt…"/"Verbindung wird getrennt…"; "Verbindung wird wiederhergestellt…" would be consistent. Out of scope for 2.0.2 unless you want it.
5. `Tested %@` -> "Getestet um %@": fine (the argument is a time). If the date style ever changes to include a date, "um" breaks; use "Getestet: %@".
6. `Part of your traffic may bypass the VPN` / `Some of your traffic does not use the VPN`: DE "umgeht möglicherweise" / "nutzt ... nicht" correct and distinguishable.
7. `because.*` keys: subordinate clause order correct ("LockPlus das Profil nicht sicher prüfen konnte", "es außerhalb von LockPlus gestartet wurde"); reason fragments in main-clause order. Good.
