# LockPlus 2.0.2 security review (Fable, round 2)

Scope: `git log f1ae738e..HEAD` (13 fix commits, HEAD 5c7fc7f3), read-only. Paths are relative to `native/` unless they start with `docs/`.

What this rests on: reading the code, the tests and DESIGN draft 10.5. I built nothing and ran no test suite. The one thing I executed was a 10-line Swift script that measured a binary-plist size (L3); its scratch directory is deleted. NE behaviour is taken from the project's own notes, not re-measured, and each finding that depends on it says so.

## Verdict

No HIGH. Two MEDIUM, eight LOW, five NIT.

- The round 1 HIGH (H1a, H1b) is fixed in the engine and the tests would catch a regression of either variant.
- Codex 3 is fixed only for the pause record. Two other unauthenticated records in `settings.json` still make the signed app start a profile (M1).
- The F7 fix has no termination condition and has never run against NE (M2).
- The new `revokeUnattended` can remove a record that NE's restart still needs, which is the plan's stop condition again, in a narrower window (L1).

## HIGH

None.

## MEDIUM

### M1. `settings.json` can still make the signed app start a profile (remaining; Codex 3 class)

The resume intent authenticates `pausedState.profileID` only. Two more records are read from the same unauthenticated file and lead to a start.

**a. `pendingResume.profileID` (direct start).**
- `App/Stores/ManagerQuiescer.swift:50-67`: `resumeAfterUpdate` reads `settings.value.pendingResume` and calls `returnOnDemand(r.onDemandEnabledIDs, thenConnect: r.profileID)`.
- `App/Stores/ConnectionStore.swift:2174`: that is `connect(target)`, an ordinary armed GUI start with the saved credentials.
- `App/SystemExtensionManager.swift:156-190, 478-479`: an activation request is submitted on every launch, and its `.completed` calls `resumeAfterUpdate`.
- Scenario: same-user code kills LockPlus (same uid), writes `pendingResume {profileID: P, onDemandEnabledIDs: [], reason: "extensionUpdate"}` into `settings.json`, and runs `open -gj -a LockPlus`. The app arms and starts P. No pause, no consent, no intent check. This is as immediate as the headless path Codex 3 described.

**b. `autoConnect.enabled` / `autoConnect.profileID` (unattended consent).**
- `App/Stores/ProfilesStore.swift:512-519` and `App/Model/ManagerConfiguration.swift:100`: the plan, and with it `providerConfiguration.onDemand`, comes from `settings.value.autoConnect`.
- Scenario: the same write with `autoConnect {enabled: true, profileID: P}`. At the next on-demand re-save the app gives P on-demand rules and the consent flag, and NE starts it unattended.
- I did not trace whether a launch alone triggers that re-save; any rule edit, pause end or deferred sync does. It is visible in the Auto-Connect pane afterwards.
- `policy.stayConnected` is in the HMAC'd metadata and is not affected.

Fix:
- Authenticate every record that leads to a start. Simplest: one HMAC'd file (or a keychain item) for `pausedState`, `pendingResume` and the Auto-Connect choice, verified before use; a record that fails restores on-demand only.
- Or move the Auto-Connect profile choice into the profile's authenticated metadata.
- At minimum list both in DESIGN §20 risk 29; today it says the pause record is the only such path.
- Tests: a forged `pendingResume` at launch arms and starts nothing; a forged `autoConnect` gives no plan.

### M2. The F7 fix reloads on every status change of an unknown connection object, with no coalescing and no stop condition (new in round 2, unverified on NE)

- `App/Stores/ManagerStore.swift:231-239`: any `NEVPNStatusDidChange` whose object is not in the current filter now calls `onConfigurationChange`.
- `App/Stores/ManagerStore.swift:458-465`: that bumps `lastMutation` (the settle clock every start waits on) and runs `loadAll()`.
- `App/AppEnvironment.swift:329-333`: then `connection.configurationChanged()` and `profiles.load()`.
- `loadAll` replaces every manager object, so each reload makes the previous generation "unknown".
- The filter's own comment (`ManagerStore.swift:120`) says stale objects of earlier loads do post status changes (spike S5). Before this fix they were ignored.

Two ways this goes wrong, depending on NE timing nobody has measured:
- If objects of a load in flight post their first status before `filter.update` (the timing the F7 fix itself assumes for the clone), every reload triggers another: a reload loop.
- If stale generations stay alive, each real status transition triggers one reload per stale generation, during connecting → connected of a kill-switch start.

Consequences if either happens: `lastMutation` keeps moving, so `waitUntilSettled` fails. The headless resume then ends with "configuration not settled" and starts nothing; GUI starts are delayed.

Related: the F8 tie-break reads `m.connection.status` at load time (`ManagerStore.swift:255-257`). If NE fills the status in after the load returns, `liveRank` is 0 for both copies at launch and NE's list order decides again. One of the two fixes is weak whichever way NE behaves.

Fix:
- Reload for an unknown object only when its status is `.connecting`, `.connected` or `.reasserting` (the F7 case is a started duplicate).
- Coalesce to one reload per second, and do not bump `lastMutation` for it.
- Add an E2E row before the RC: idle app, count `loadAll` calls over 60 s after launch and across one connect/disconnect; it must be bounded.

Tests: the unit tests use fakes that never emit an unknown object's status, so they cannot catch this.

## LOW

### L1. `revokeUnattended` can drop a record that NE's restart still needs (new in round 2; stop-condition class)

- `App/Stores/ProfilesStore.swift:709-715`: the app sends every profile without a plan, whatever its NE status, after each reconcile and each on-demand re-save.
- `TunnelController.swift:1326-1336`: the extension keeps the record only if `session?.key` is that key at that instant.

Three windows where the session is not live but NE will still restart it:
- **Crash, then app launch.** An unattended kill-switch session whose rules went away (H1b) loses its extension process. If the user opens LockPlus before NE's restart arrives, hello → reconcile → revoke finds no session and drops the record. NE's restart (nil options, no rules) gets 225 and the Mac is open. The window is short online. It is long if the crash happens offline: NE restarts only when a network returns (E2E-4 200011).
- **A replay waiting in the guard.** `TunnelController.swift:276-281` decides `.replay` first; the start can then wait up to the 5 s stop cap in `await stop(reason: .superseded)` (`:356`). A revoke in that wait deletes the record, the start goes on with `admission == nil`, and the session runs with no record. Its next restart is refused.
- **Controlled end with a restart to come** (`noNetwork`, `providerFailed` under the kill switch): same as the first, with the process still alive.

All need H1b's precondition plus a revoke at the wrong moment, so LOW. The outcome is the one the plan stops for.

Fix:
- App: leave out of the list any profile that is not `.disconnected`/`.invalid`, is the `networkRestartHolder`, or has `crashDecision == .expectSystemRestart`.
- Extension: skip a key that has a start in `guardedStarts`; on `.replay`, carry the matched record and write it back at admission if it is gone.
- Extension: refuse revokes (busy) for the first seconds of a process that has admitted no start yet.
- Tests: revoke between a persisted record and its replay in a new controller; revoke during a replay's guard wait.

### L2. An unattended record can stand for much longer than risk 29 (1) says (new in round 2; documented, but understated)

- DESIGN §20 risk 29 (1) says the record goes "at the latest the next hello". A hello happens only at app launch or extension activation; a menu-bar app can run for weeks.
- Nothing clears the record at a reboot or logout, and `stop` with no session clears nothing (`TunnelController.swift:1310`).
- Scenario: a kill-switch Auto-Connect profile connects on demand. The user turns Auto-Connect off while connected, later shuts the Mac down still connected. After the boot the record is in `state.plist` and the profile has no rules. Any local user, or same-user code at login, runs `scutil --nc start` and is admitted as `.replay` (`StartAuthorisation.swift:74`), with the owner's saved credentials. It works repeatedly until the owner's user stop or a revoke while that profile is idle.
- So the answer to "can one legitimate auto-connect become a standing authorisation": yes, in this case.

Fix:
- Bind every record to the boot session (`kern.bootsessionuuid`); NE never replays a session across a reboot. This also shrinks L8 from round 1.
- App: send a revoke when a planless profile reaches `.disconnected` and no system restart is expected, and after its own user stop.
- Correct the wording of risk 29 (1).

### L3. `revokeUnattended` fails for good once about 380 profiles have no plan (new in round 2)

- `RequestReplies.swift:193`: `maxProfiles = 500`. `LPWire.swift:59-66`: the method's request cap is the default 16 KiB.
- Measured: 380 UUIDs encode to 16,406 bytes, 500 to 21,566. The extension rejects the request before decoding (`payloadTooLarge`).
- `ProfilesStore.swift:712-714`: the failure is a log notice. Every later revoke fails the same way, so the Codex 4 revocation silently never happens.
- A provider zip of 400–500 servers is a normal import (the zip cap is 500 entries).
- Beyond 500 profiles `prefix(500)` also never revokes the rest.

Fix: send the complement, the few profiles that do have a plan, and let the extension drop every other unattended record of the caller's uid. Or raise the cap for this method and page. Add a wire test that a maximal request fits its `requestLimit`.

### L4. An unattended admission overwrites an armed record and loses its nonce (new in round 2, unverified NE behaviour)

- `TunnelController.swift:279, 382`: `.unattended` records `nonce: nil` over whatever was there.
- Scenario: the user connects an Auto-Connect kill-switch profile from LockPlus (armed, nonce N). The session ends without a user stop and on-demand brings it back (record now nil). If NE ever restarts that session with the options of the earlier manual start, `rec.nonce == nonce` fails and the start gets 225.
- I have no evidence which options NE replays after an on-demand restart. S2 E1 measured only the plain crash restart.

Fix: keep both facts in the record (`nonce` plus an `unattended` flag) and never discard a nonce except on a user stop, removal or wipe. Add the case to the E2E-8 S rows.

### L5. Resume intent: replay, laundering on a pause extension, and a silent loss when the key is unavailable (new in round 2)

- **Replay within 7 days** (documented, risk 29 (2)). A genuine record for (P, T) restarts P any time up to T + 7 days, including after the user disconnected P on purpose. A real one-shot is cheap: put a random per-pause value in the keychain, include it in the MAC, delete it at resume.
- **Laundering.** `ConnectionStore.swift:2114-2118`: a second pause while paused keeps `old.profileID` from the stored record and mints a fresh intent for it, without checking the old record's intent. Same-user code writes a pause record naming P with no intent; if the user extends that pause, the app signs it. Fix: carry `old.profileID` only if the old intent verifies for the old end; else use `active`.
- **Key unavailable.** `ProfileRepository.swift:213-216` returns false when the keys can't be loaded. `HeadlessResume.swift:103-108, 181-182` then drops the target and clears the pause record: the paused profile is never reconnected, with only a fault log. `ConnectionStore.swift:2118` (`try?`) writes a record with no intent if the key read fails at pause time, with the same end. The GUI's note then says the record "was changed outside LockPlus", which is wrong for this case and for a record older than 7 days. Fix: treat "can't verify" as retryable (like `.armUnavailable`), and fail the pause if no intent can be made.
- Not bound to the revision. I see no harm in that: it is the owner's own profile.

Tests: profile, end, age and another keychain are covered. Missing: the GUI's resume with a forged record, the pause-extension case, a key-load failure.

### L6. Round 1 L4 is only partly fixed (remaining)

- `ConnectionStore.swift:1442`: the refusal needs `settings.value.extensionHandOver`, a marker from the unauthenticated settings file (`AppSettings.swift:140`). I did not trace whether the marker spans the whole time the old extension runs with its replacement pending. If it is false while `.legacyExtension` is reported, the kill-switch start goes out without a nonce as before.
- `HeadlessResume.swift:128`: `case .legacyExtension: break`. The headless agent has no such guard at all.

Fix: refuse a kill-switch start on `.legacyExtension` unconditionally, in both places. The test `noKillSwitchStartWithoutANonceDuringAnExtensionUpdate` covers only the GUI with the marker set.

### L7. Opened files can still replace the sheet the user is looking at (remaining, round 1 L2)

- `ImportCoordinator.swift:266`: `isBusy` counts a shown sheet and an open event's own analysis, not an analysis the user started (`importFiles`, `:204`).
- `:336-349`: `analyseAndPresent` sets `model.preview`/`model.batch` unconditionally.
- Scenario: the user drops their own file; while it is being checked, `open -a LockPlus evil.ovpn` arrives. Both analyses run. If the user's sheet appears first, the opened one replaces it a moment later. The new sheet does carry "Opened from", no default button and the 1 s delay, so the round 1 harm is reduced, not gone.
- `openQueue` (`:252`) is unbounded: 1000 open events mean 1000 sheets to cancel.
- `:211`: a read that never returns (a stalled network mount) leaves `openingEvent` true, and no later open event is ever shown.

Fix: one "analysing" counter for every import; present an opened import only when no sheet is up; cap the queue (for example 5, then one "too many" message); give the detached read a timeout.

Tests: `aSecondOpenEventQueuesBehindTheShownSheet` covers a shown sheet only, not an analysis in flight.

### L8. A file that hangs the check now costs every launch (new in round 2)

- Before round 1 a timeout refused the file. Now it is saved as "Not yet verified".
- `ProfilesStore.swift:857-858`: `reconcile` awaits `verifyPending()` before it lists, provisions, removes or revokes anything.
- Each try can take two client timeouts (12 s each), and a profile gets two tries per run (`:985-986`): about 48 s per hanging profile per launch, with the validator gate held. The counter is memory only, so it repeats at every launch, without limit.
- A zip of such files, confirmed once by the user, delays provisioning after every launch by minutes to hours.
- It never becomes a provision: an unverified profile is refused by `provision` (`:820`).

Fix: run `verifyPending` after the provisioning part of reconcile; cap timeouts per run in total (for example 3); persist a timeout count and stop retrying after a few launches, with a manual "Check again".

## NIT

- **N1.** `ValidatorServiceHandler.swift:53-56`: the service exits 250 ms after its `.timeout` reply, and the client reconnects at once (`ValidatorClient.swift:108-113`). The next try can land on the dying process and spend its single crash retry there. Wait for the old connection's invalidation, or 300 ms, before reconnecting.
- **N2.** `ProfilesStore.swift:906-927`: the migration unseals and normalises every OpenVPN profile on every reconcile, and logs an error each time for one it can't migrate. Remember the checked revision.
- **N3.** `ProfileRepository.swift:208-216`: the resume intent uses the metadata MAC key. The message prefix keeps the two apart (metadata is JSON), but a separate HKDF info string costs one line.
- **N4.** `ImportCoordinator.swift:292-303`: "Opened from" shows an attacker-chosen path with middle truncation. It is a hint, not provenance; a directory named `~` reads like the home folder.
- **N5.** FIX1-REPORT says only HEAD was test-run and no fix has run against NE. The new E2E-8 rows are the only evidence for H1a/H1b replay, F6–F8 and the `NWPath` interface under `includeAllNetworks`.

## The brief's questions

- **Resume-intent key handling.** The key is the keychain-held metadata MAC key, HKDF-derived, never written to disk. Same-user code can't forge an intent. It can replay one (L5) and get one signed (L5 laundering). GUI and headless share one check. `onDemandEnabledIDs` is not authenticated, but it only re-enables rules a profile already has, which `scutil` could start anyway.
- **`revokeUnattended` callers.** Only a peer that passes `APP_REQ` and the hello gate. It is scoped to `peer.uid` (`EngineServiceBackend.swift:127-131`), so another user can't touch your records, and same-user code can't call it. No test exercises this through the backend; the engine test passes the uid directly.
- **Validator respawns.** Bounded per request; a crash can't become "Not yet verified → provisioned", because provisioning needs an accepted verdict on the same revision and digest.
- **Migration.** Sound for security. Rollback of a whole profile to an older sealed revision is outside this change.
- **Stray tie-break.** I found no way for same-user code to make the app remove the protective copy while keeping a weaker one at idle: equal revisions prefer the more protective, a live weaker copy is healed at `.connected`, and strays are removed only at idle. A forged higher revision quarantines (documented).
- **Open-document 1 s delay.** Works as described for a sheet that appears on its own. The gap is replacement during an analysis (L7).
