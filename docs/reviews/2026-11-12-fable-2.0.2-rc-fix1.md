## 1. Validator: APP_REQ per connection

All five points hold.

- **Every peer must pass APP_REQ before any message reaches the handler.** `ValidatorServiceHandler.swift:199-204`: `setCodeSigningRequirement(peerRequirement)` is the first statement of `shouldAcceptNewConnection`, before `exportedInterface`, `exportedObject` and `activate()`. It is the only delegate and the only accept path, and `ValidatorProcess.swift:19-22` builds it with `APP_REQ`. The initializer has no default requirement.
- **No window.** The connection is not activated until the requirement is set, and nothing else holds a reference to it before that.
- **A failing requirement delivers nothing.** Confirmed by the package test above: an unsigned peer against the Release APP_REQ gets no reply and its connection ends with an error.
- **VALIDATOR_REQ on the client is unchanged.** `ValidatorClient.swift` is not in the diff; line 220 still sets it once before `activate()`.
- **APP_REQ still carries the floor and the right signer.** `Shared/` is a synchronized group of the LockPlusValidator target; `LP_DEV_SIGNING` is only in Debug.xcconfig. The floor is 200027 consistently in `SigningRequirements.swift:26`, `common.sh:21`, RequirementTests and LPWireTests.
- **The hosted test starts the real service.** `EmbeddedValidatorServiceTests` connects with `NSXPCConnection(serviceName:)` to the `.xpc` in the test host and requires a new service pid that is still alive one second later. It catches the crash-at-launch regression. It does not catch an enforcement regression (L3).
- **Context for severity:** the service is app-private (launchd scopes it to the host app), sandboxed, network-less and holds no secrets, so APP_REQ here is defence in depth.

## 2. Headless resume agent

The mechanism is correct.

- Main-actor work runs under `RunLoop.main` in default mode, so main-queue blocks run on the main thread and NE's `queue: .main` observer runs inline.
- The deadline is on a private serial queue and is armed before the work is scheduled.
- `Once` (a Mutex) gives exactly one `end`. Double exit is not possible: the loser of `claim()` does nothing.
- `_exit` on timeout is right: no atexit handler can wait on a stuck main thread.

### State after a hard timeout (`_exit` at 5 s, now possible at any instruction)

| State | Result |
|---|---|
| Half-written settings.json | Not possible. `AtomicFile.write` is temp file, `F_FULLFSYNC`, `rename`; the file is the old or the new one. An orphan temp file can remain (N5). |
| Exit during a keychain call | Safe. `consumeRecord` is one `SecItemDelete`, atomic in securityd; the agent never seals or rewrites a value. |
| Sealed pause record | The agent never seals. A killed run leaves `pausedUntil`, `pausedState` and the tag untouched. |
| `pauseValueOwed` | Consistent. `spend()` writes a change before it returns. A kill between a failed delete and that write loses nothing, because nothing else changed on disk and the next run repeats the same spend. A kill after a successful delete while disk still says "owed" makes the next run delete again, which is harmless. |
| Issued arm, no start | Safe. The nonce dies with the process, the arm lapses after 15 s, and the next run is at least about 60 s later. This is why the hard deadline must stay well below 15 s. |
| One-time value spent, start not issued | Inconsistent in a narrow window: **L1**. |
| Start issued, final write not done | Benign but mislabelled: **L2**. |
| GUI instance lock | Released by the kernel at exit. |

### Is 5 s right?

In the safety direction, yes, and it should not be raised. Arm cap 2 s, settle cap 2 s and the soft deadline (`budget - reserve` = 4 s, `HeadlessResume.swift:85`) all fit inside it. The arm (15 s) can never outlive a run into the next one, and a start can never be issued with an arm older than about 5 s. The 60 s the brief originally suggested would break the "arm lapses before the next run" argument.

In the liveness direction it is unproven: see M1.

## Findings

### HIGH

None.

### MEDIUM

**M1. A slow run ends the pause for good without reconnecting; it is not retried.** `native/App/Headless/HeadlessResume.swift:266-269` and `:222-243`. Not introduced by this diff, but until now the agent always deadlocked before reaching it.

- **Scenario:** the pause of a manual kill-switch profile ends while LockPlus is closed, and the run is slow. The typical case is the coalesced run right after wake, when nesessionmanager and securityd are slow. If `loadAll`, the intent check, the arm, the on-demand save, `store.load()` and `prepareForStart` (each uncapped, with 0.5 to 1 s of sleeps in `ProfilesStore.swift:759/767`) have used up the 4 s soft deadline, or the at-least-1 s settle does not complete in what is left, `verifyForStart` throws "configuration not settled".
- **Result:** the catch spends the one-time value, clears `pausedUntil` and `pausedState`, and unregisters the agent. A profile without on-demand rules stays disconnected, with no retry and no Problems line, because the GUI later finds no pause. That is the same end state as S9, without a hang.
- **Estimated healthy path:** about 2.5 to 3.5 s (my estimate from the sleeps and caps; nobody has measured it) against a 4 s budget.
- **CHANGELOG is inaccurate for this path:** "gives up within 5 seconds, and the next minute's run tries again" is true only for the hard timeout.
- **Fix:** treat out-of-time as retryable. When `cap <= 0` or the settle times out, return a new retry outcome before any `spend()`, as `.armUnavailable` does: the pause stays, the agent stays registered, and the next run finds the on-demand saves done and the configuration settled. Keep the terminal path for definite failures only (profile unreadable, flags still wrong after repair). Then correct the CHANGELOG sentence or leave it once it is true.
- **Timing:** it can go into 200027 if you want a single RC. Otherwise it is acceptable to build first and decide on the measured S9 timing.

### LOW

**L1. A hard timeout between the intent spend and the start burns the intent.** `HeadlessResume.swift:216-217`.

- **Scenario:** the settle returns near 4 s and the keychain delete takes about 1 s (a securityd stall), so `_exit` lands after `SecItemDelete` succeeded and before `managers.start`.
- **Result:** the next run finds no one-time value, gets `.changedOutside`, logs the "pause record without a valid intent" fault, clears the pause and does not restart the profile. Same end state as M1, with a misleading tamper log.
- **Fix:** after the settle, check the time left to the hard deadline. If it is under about 500 ms, return the retry outcome from M1 without spending. This is one guard next to the M1 change.

**L2. A hard timeout after the start but before the final write is read as tampering by the next run.** `HeadlessResume.swift:138-146`.

- **Scenario:** `_exit` lands between `managers.start` (line 217) and the final save (line 240).
- **Result:** the next run finds the value spent, logs the fault, sets `target = nil`, and then re-enables every other profile's on-demand beside the running target (line 193), which is the E2E-3 situation. The "previous run was ended after its start" branch at line 213 is unreachable for this case since the intent became one-shot.
- **Fix:** before `checkResumeIntent`, if the recorded profile is already active, treat it as restarted: spend, keep `target`, skip arm and start.

**L3. The hosted test cannot see an enforcement regression in the real service.** `native/Tests/LockPlusTests/EmbeddedValidatorServiceTests.swift:68-71`.

- **Scenario:** the Unit plan's host is ad hoc signed. If the service stopped applying APP_REQ, the host would get a hello reply and the test would still pass, because the reply branch only checks wire and build.
- **Fix:** check whether the host itself satisfies APP_REQ (`SecCodeCopySelf` plus `SecCodeCheckValidity` with `SecRequirementCreateWithString(APP_REQ)`), then assert that a reply arrives if and only if it does.

**L4. The `.finished` end is not covered by the deadline.** `HeadlessRunner.swift:27-33`, `HeadlessResume.swift:294`.

- **Scenario:** the work returns in time and claims `Once`; `exit(0)` then runs atexit handlers and static destructors while other threads are live. If that blocks, the watchdog's claim fails and nothing ends the process, so launchd never starts another run. That is the S9 failure class again, though unlikely.
- **Fix:** make the deadline unconditional. At the deadline call `_exit(0)` whether or not `.finished` was claimed, or use `_exit(0)` for `.finished` too; the outcome is already logged and the settings are fsynced.

### NIT

- **N1. Success log line may never appear.** `HeadlessResume.swift:243` then `:283`: `agent.unregister()` kills the process by the code's own comment (line 35), so `resume agent: resumed…` is only logged if that kill loses the race. FIX-E2E-REPORT tells the S9 re-run to look for that line. Log the outcome before the unregister, or judge S9 by the NE status and `startTunnel` in the extension log.
- **N2. Timeout exits with status 0.** `HeadlessResume.swift:297`: use a non-zero status (for example 75) so `launchctl print` shows the last run timed out.
- **N3. Deadline timer has leeway.** `HeadlessRunner.swift:26`: `asyncAfter` can fire up to about 10 % late (the design's own S2 measurement). Harmless against the 15 s arm, but a `.strict` `DispatchSourceTimer` would match D9-5.
- **N4. Possible false failure in the hosted test.** `EmbeddedValidatorServiceTests.swift:44, 74`: if anything in the test host ever connects to the validator before this test, the pid is already in `before` and the test fails although the service is healthy. Accept "a pid running this executable exists" when `before` is non-empty.
- **N5. Orphan temp files.** `AppDataStore.swift:38`: a hard timeout mid-write leaves `.settings.json.<uuid>.tmp` (0600, same content class as settings.json). Nothing sweeps them; sweep at GUI launch.
- **N6. `runMainLoop()` and the live `main()` are untested.** `HeadlessRunnerTests` runs under the test host's own run loop, so only the lint rule and the VM S9 row guard the real entry point. Acceptable.
- **N7. DESIGN.md still prescribes the crashing call.** Lines 1128 and 1973 say `setConnectionCodeSigningRequirement` on `NSXPCListener.service()`. The fixer's hand-back already lists this for the integrator.

## 3. Editor-open tests and the log line

- **Log line** (`SystemHooks.swift:48-54`): logs only the NSError domain and code as public. The reason string, which names the profile, is not logged. No secrets. It applies to every `authenticate` caller (edit, export, duplicate, show password, reinstall, uninstall), which is fine.

They do not exercise `editConfig` itself (profile lookup, LAContext, `becomeRegular`), so E2E finding 3 is still unexplained rather than disproved.
