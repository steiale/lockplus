## FINDINGS (most severe first)

**R1 HIGH — F1 is not closed: the 1.5 s grace is shorter than NE's measured restart.** CS:796-811 (`restartAfterCrashIfNeeded` → `.skip` → `restoreIfIdle()`), CS:832 (`grace = 1500 ms`).
Measured (DESIGN LK-02 outcome ~line 2896; native/e2e/RESULTS-E2E-1.md kill -9 row; S2 E1 row ~2881): `.disconnected` at +5.0–5.2 s after the kill; packets flow on en0 until +7.23 s (26) / +7.31 s (27), i.e. the restarted session's block (= NE's new pending start) lands **≈2.0–2.3 s after `.disconnected`**; S2 E1's open window is 2.45–2.86 s. The "~1 s after `.disconnected`" in DESIGN §10.4 and CS:793 is contradicted by the same document's numbers; the "new provider PID 1 s after the kill" is launchd relaunching the sysext process, not the session restart. So for a manual kill-switch profile X (no on-demand rules): fresh crash → fetch (+XPC `lastLinkInterruption`) → grace 1.5 s → status still `.disconnected` → `restoreIfIdle` → `saveOnDemand(A)` = a full `saveToPreferences` of A with on-demand ON at ≈1.6–1.8 s, i.e. 0.2–1.2 s BEFORE NE's restart — the exact 200003 mode (a config change inside the pending kill-switch start; 16 ms was enough), and afterwards A is enabled beside the restarted X for the whole session (no post-start pause by decision) → next en0 change blocks X. DESIGN calls "a restart later than the grace" the residual; it is the common case.
Fix (the alternative you proposed, recommended): when the crash is fresh and `decide` says NE restarts (`includeAllNetworks && !onDemandEnabled`, today `.skip("no on-demand rules active")`), do NOT restore on that disconnect: keep `awaitingRestart[id]`, clear it in `handle()` when `status.isActive` (then `statuses` keeps `othersBusy`), and arm a fallback (reuse `startingTimeout`, 30 s; well above 2.9 s) that removes it and restores if still `.disconnected`. Keep the 1.5 s grace for the app's own `.restart` decision. Make `CrashRestartPolicy.decide` return a distinct case (`.expectSystemRestart`) instead of matching the string. Other skips (`no kill switch`: NE restarts only with the flag; `user action`, `restart limit`: nobody restarts) restore after the grace as now. Test: emit NE's `.connecting` 3 s after `.disconnected` with grace 300 ms and assert no save in between.

**R2 HIGH — Auto-Connect turned on / re-pointed while another profile runs is never restored (regression of the record-only restore).** CS:512-522 (`restorePaused` iterates only the record), CS:179 (retry only while the record is non-empty), PS:402-411 (`resaveOnDemand` saves the held-back plan), UB:301.
Scenario: X connected (manual). User enables Auto-Connect for B (or moves it from A to B) → `resaveOnDemand` saves B with `enabled=false` (`onDemandHeldBack`). B was never paused so it is not in the record; A's record entry is dropped (plan nil). X ends → `restorePaused`: nothing. Next launch: nothing. B stays off forever; the pane shows "Auto-connect is off; LockPlus couldn't turn it back on." (UB:247) and nothing ever retries. Before this range the restore was derived from `settings.autoConnect` and covered this.
Fix: make the restore set = record ∪ { p | `profiles.onDemandPlan(for: p)?.enabled == true` && manager off } (that is `onDemandNeedsRestore` without the busy guard), and call `restoreIfIdle()` from `handle()` whenever `!isBusy` (cheap: `saveOnDemand` skips no-op saves). Together with R3 (deferred `resaveOnDemand` runs at idle) this also closes it. Add a test: enable Auto-Connect for B while X is connected; X disconnects; expect B on.

**R3 MEDIUM — F5c unfixed: `resaveOnDemand` lands a save of another manager inside the pending start.** PS:402-411, UB:273-283, UB:301, AE:399 (`addCurrentNetwork`). Only `load()` honours `mutationsDeferred` (PS:126-146). A click on any Auto-Connect control, or "Add Current Network", during X's start window (prepare + resolve + 1 s settle + NE's async processing) issues `managers.save(A, …)` — a configuration change of ANOTHER manager while the kill-switch start is pending: the 200003 failure. While X is connected it is the unmeasured U2 case.
Fix: `resaveOnDemand` checks `mutationsDeferred()` and, if busy, sets `hasDeferredSync = true` and returns; the idle tail of `restoreIfIdle` (CS:508) already re-runs `load()`; make it run `resaveOnDemand` too (or have `load()` cover it — the plans are recomputed at idle anyway, and on-demand is held back while busy, so nothing is lost).

**R4 MEDIUM — launch ordering: `profiles.load()` runs before `connection.start()`, so `isBusy`/`holdsBackOnDemand` are false while a session from the previous instance (or System Settings, or the headless agent) is running.** AE:245-246, CS:437-440 (`othersBusy` reads `statuses`, filled only in `start()` CS:107).
Scenario: X connected (restarted by the headless agent, A recorded as owed), GUI launches: `load()` → `isBusy == false` → orphan sweep + drift heals run (saves of other managers beside a connected X, U2) and, if A's manager is behind or drifted (PS:328-333; nehelper's rewrite is routine on 26/27), `syncManager(A)` saves A with `onDemandPlan` → `onDemandHeldBack(A)` false → **on-demand ON beside running X**. Then `connection.start()` sees X active and keeps the record; A is already on.
Fix: `othersBusy` should also read the live manager statuses: `managers.managers.contains { $0.profileID != id && $0.status.isActive }` (ManagerSnapshot.status is live after `loadAll`). One line, independent of launch order. Add a test: X `.connected` in the fake, A's manager behind, `profiles.load()` before `connection.start()`; expect A off.

**R5 MEDIUM — `resume()` enables everything directly when `pausedState.profileID == nil` even if something is active or starting.** CS:685-695; also MQ:54-55 (`resumeAfterUpdate` enables all then `connect`).
Scenario: user clicks Pause Protection while X is in its start window (no status yet → `active == nil` → `pausedState.profileID == nil`; `pause` does not cancel the start, X connects and runs through the pause). Pause expires → `target == nil` → `later = []` → `setOnDemandEnabled(true, A)` beside connected X. Narrow window but deterministic. MQ: enable-all then `connect` → `pauseOtherOnDemand` turns them off again (churn of 2 saves per config, and an on-demand start of A can fire in the ≤1 s before the pause; F6 then turns it into a switch, with A stopped and nothing recorded for it).
Fix (also a simplification): `resume()` = `addToPauseRecord(ids)`; `if let target { connect(target) } else { restoreIfIdle() }`. `restoreOwnOnDemand` (CS:429) already re-enables the target's own on-demand inside its start; the rest returns when idle. Same for MQ.resumeAfterUpdate. Drop the `later` split and the direct loop. Test the hand-back (today `aUserPauseTakesOverTheRecord` stops at `pause`).

**R6 MEDIUM — headless resume starts with no settle after its own saves.** HR:73-80: `setOnDemandEnabled(true, target)` (a save), `verifyForStart` → `prepareForStart` (a save if behind, 0.5 s settle only then), then `managers.start` immediately. The GUI waits `waitUntilSettled(1 s)` after the same sequence (CS:372-375). Same-manager saves before a pending start are unmeasured (E9 covers connected only). Fix: `await managers.waitUntilSettled(store.settleBeforeStart)` before `managers.start` (fits the 5 s watchdog: loadAll + ≤2 saves + 1 s); on timeout the watchdog exits without starting = fail-closed, next minute retries.

**R7 LOW — F9 timeout races the start it was meant to guard.** CS:478-485 clears `starting` and restores A; the in-flight `startNow` Task (CS:355-389) has no `starting.contains(id)` check after its awaits and still calls `managers.start` → X beside A enabled. Needs a pre-start phase > 30 s (stale retry + loadAll on a wedged nesessionmanager, or R8). Also `beginSwitch`'s 22 s fallback (CS:346-349) calls `startNow` again while the first Task may still be in its window → two `start` calls. Fix: `guard starting.contains(id) else { return }` after each await in `startNow`; in the F9 timer, also mark the start as abandoned.

**R8 LOW — `waitUntilSettled` is unbounded.** MS:349-358: every `NEVPNConfigurationChange` (our echoes, nehelper rewrites, another user's configurations of our bundle id) resets `lastMutation`; a steady stream never settles; `starting` then holds A back until R7 fires. No deadlock (never called under the lock). Fix: cap the total wait (e.g. 5 s) and on the cap `fail(id, .killSwitchNotApplied-like "configuration not settled")` — fail-closed, noted — rather than proceed.

**R9 LOW — `awaitingRestart` can stick.** CS:199-202: if `fetchLastDisconnectError` never calls back (wedged nesessionmanager) the id stays in `awaitingRestart` → `othersBusy` forever → no restore, `load()` deferred forever, pane says "resumes when you disconnect X". Bound it (`withDeadline` 10 s → treat as non-crash).

**R10 LOW — `load()` checks `mutationsDeferred()` once (PS:126) and `restoreTask = nil` precedes the trailing `load()` (CS:506-508).** A start that begins after the check but during load's saves is not awaited by `pauseOtherOnDemand` (CS:405) and load's later saves can land after `managers.start`. Fix: re-check `mutationsDeferred()` before each save/remove in `load()`; set `restoreTask = nil` after the load.

**R11 LOW — settings durability: a queued async snapshot can overwrite a later synchronous write.** SS:28-42: `persist()` captures `snapshot = value` at update time; `addToPauseRecord`/`dropFromPauseRecord` call `update` (queues S_n) then `writeSynchronously` (S_n). Sequence update(S1)/sync(S1)/update(S2)/sync(S2)/async(S1)/async(S2): a crash between the two async writes leaves S1 on disk (e.g. a record without A → A off after relaunch if X ended, with no retry per R2). Fix: let the async writer read `value` at write time (latest wins), or skip the queue when a sync write is pending.

**R12 LOW — extension arrival retry nits.** TC:243-252 `beginStart` calls `startPathWatcher()` without `stopPathWatcher()` first (`guard pathTask == nil`, TC:846): a watcher that outlived a previous session keeps a stale `lastPath` baseline → the first path of the new start reads as an "arrival" → one spurious retry (bounded). TC:881-884 `isArrival` compares `Set(interfaces)` of "en0:wifi"-style strings: a type-label change of the same interface counts as an arrival. Arrival + the app's push-on-arrival (2 s settle) can restart the attempt twice per arrival (each bounded at 10). Otherwise correct: epoch bump via `teardownAdapter` (TC:998) drops the old attempt's late events (same pattern as `pushEndpoints` TC:1330-1338); `broker.live == nil` and `answerAttempt` guards match PF-R2; OpenVPN in flight never replaced; stop() nils the session/phase `.stopping` so a settled path after stop does nothing; `.dnsResolutionFailed` excluded (L4). Fix: `stopPathWatcher()` before `startPathWatcher()` in `beginStart`; compare interface names only.

**Nits.** CS:179 calls `restoreIfIdle()` on every status event while recorded (observable `restoring` flips true/false per event). CS:420-425 `failPause` leaves the (never paused) id in the record until idle and `holder(of:)` then says "resumes when you disconnect X" although nothing is off — drop the entry in `failPause` when the manager still has on-demand on. CS:470-471 double write per record change (update + sync). HR:111 `store.load()` rebuilds `credential-facts.json` from every OpenVPN secret if the file is missing (L3 cost, no exposure).
