Review of e321e10 (read-only). Verdict: the fix closes the restore-at-`.disconnecting` bug on every teardown path (the gate is the live status via `isLive`, not the entry, so crash / NE stop / user stop / switch / quiesce / delete / Pause all hold the restore until a handled `.disconnected`). One HIGH regression, rest LOW.

**HIGH — stale `.disconnecting` in `statuses` keeps busy forever (auto-connect off until relaunch), UI-reachable via Delete of a live profile.**
- `ConnectionStore.statuses` is never pruned (only written: `ConnectionStore.swift:167`, `:196`). `SerializedVPNManager.loadUnlocked` drops `reported[id]` for a vanished manager but emits nothing (`ManagerStore.swift:407-408`); `remove` likewise (`:439-446`); `NEManagerStore.statusNotification` drops events for ids no longer in `byID` (`:162-165`), and `remove` nils `byID[id]` right after `removeFromPreferences` (`:279-284`).
- `ProfilesStore.delete` (`ProfilesStore.swift:551-564`) does `managers.stop(id)` and then removes at once (`onDemandHeldBack(id)` excludes the profile's own live status), bypassing `ConnectionStore.stop()` so `userStops` is not set. Real NE sequence: `.disconnecting` lands within ms (during the `await removeFromPreferences`) → `handle` sets `statuses[id] = .disconnecting`, `holdTeardown` arms `.awaitingRestart`; removal completes; `.disconnected` ~1.4 s later is dropped (byID gone). `configurationChanged` → `dropVanishedRestarts` clears the entry, but `statuses[id] == .disconnecting` stays, `sawActive` too. `othersBusy` (`:603`) is true until relaunch: no restore of the pause record, every heal/sweep deferred, every Connect of another profile waits `stopTimeout` 22 s via `stoppingOther` (`:468-471`) then "starts anyway".
- Surfaced, but misattributed: `busyReason` (`:642-645`) → profile deleted, manager gone → `.unaddressable` → pane says "A VPN configuration LockPlus can't address is active". Same path when another user deletes their configuration mid-teardown → `.anotherUser` forever.
- Before this commit the likely stale value after a delete was `.disconnecting` (not busy under `isActive`), so this is new in practice; stale `.connected` was a rarer pre-existing race. Delete is not gated on a live session (`SidebarView.swift:86,94`, `SceneSupport.swift:160` → confirmation → `AppActions.swift:266`).
- Fix: (1) in `dropVanishedRestarts()` (`:798-803`, runs on every status event and `configurationChanged`) also drop `statuses`, `sawActive`, `reachedConnected`, `sessionKillSwitch` for ids not in `managers.managers`; (2) have `SerializedVPNManager.remove` and `loadUnlocked` emit `.invalid` for a vanished reported id so `handle` sees the end; (3) `delete` should go through `ConnectionStore.stop()` (user stop) and wait for `.disconnected`/`.invalid` before `remove` (also avoids the spurious `.stoppedUnexpectedly` notice + fetch the deferred-removal branch produces today). The fakes hide this: `FakeVPNManager.stop` sets `.disconnected` synchronously (`AppRootFakes.swift:114`). Add a test: delete the connected profile, never emit `.disconnected`, expect the auto profile restored.

**LOW — U10 no-live-link branch (`:305-312`) over-triggers on any non-user stop with a sticky 12.** The 12 persists NE-side after one crash until another error. Every later non-user stop of a no-rules kill-switch session (System Settings disconnect, `ManagerQuiescer.quiesce` stop `ManagerQuiescer.swift:36`, delete's stop in the deferred-removal branch — none set `userStops`) costs 10 s `.awaitingRestart(expectsRestart: true)`: hero/menu show "Waiting for X's tunnel process to restart…" (`ConditionCopy.swift:114-116,141`) with no Cancel (`DerivedState.swift:223`) and Connect disabled for every profile including X (`connectHold` exempts only `.readingDisconnect`, `:781-785`). Cost is delay + misleading copy, no safety issue. Also `crashes.crashed` isn't recorded there, so a real NE restart gives `.connected` not `.reconnectedAfterRestart` (harmless, inconsistent). Fix: hedge the copy (a distinct reason, e.g. `.mayRestart`: "Checking whether X restarts…", Cancel allowed), and make the quiescer/delete stops user stops.

**LOW — same-profile Connect during a crashed no-rules kill-switch teardown is still offered** (`connectHold` nil for `.readingDisconnect`, asserted in `aConnectDuringACrashedTeardown` `E2E4FixTests.swift:728`). Its prepare/pause/settle/start then run inside NE's ~1 s restart window; benign in practice (NE's `.connecting` clears our `.starting` entry during the settle, `prepareForStart` saves only when behind, `keep` skips crash handling) but contradicts the premise of the U10 branch. Consider holding the same profile too when `sessionKillSwitch[id] && !onDemandEnabled` during the teardown/fetch phase.

**LOW — `.disconnecting → .invalid` with the manager still present:** the `holdTeardown` entry (22 s) is then the only hold on other profiles' Connect; `sawActive` keeps the id. Rare; acceptable with the HIGH fix (an `.invalid` handled as session end).
