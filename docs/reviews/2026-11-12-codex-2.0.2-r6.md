**1. MEDIUM — Loading the new revision can shield an old answer from invalidation. New in round 5.**

[TunnelController.swift:666](native/Packages/TunnelEngine/Sources/TunnelEngine/Controller/TunnelController.swift:666), [TunnelController.swift:1983](native/Packages/TunnelEngine/Sources/TunnelEngine/Controller/TunnelController.swift:1983).

Concrete sequence:

1. Revision 1’s server prompts; the answer is stashed for its retry.
2. Provisioning writes revision 2’s payload, but its controller notification has not run yet.
3. The retry reads revision 2’s index entry and sets `loadedRevision = 2`, retaining revision 1’s stash.
4. `payloadCommitted(revision: 2)` arrives while the retry awaits credentials. Its comparison now fails: `2 > 2` is false.
5. The adapter receives revision 2’s payload with revision 1’s answer, potentially including its response, cookie and carried credentials.

Previously, the comparison against the configuration’s revision invalidated the stash in this ordering. The new field describes the retry’s payload, but does not bind the answer to its originating payload.

**Fix:** Bind each stash to its prompt’s revision and reject a mismatch when loading the next attempt. Read payload bytes and their revision atomically. Add a regression that holds the retry’s credential read after it loads revision 2, then delivers the commit notification.

**2. MEDIUM — The credential revision check and write remain separate operations. Incomplete fix for round-5 #6.**

[TunnelController.swift:1845](native/Packages/TunnelEngine/Sources/TunnelEngine/Controller/TunnelController.swift:1845), [SystemKeychainSecretStore.swift:216](native/Packages/TunnelEngine/Sources/TunnelEngine/Secrets/SystemKeychainSecretStore.swift:216).

The second `entry()` check can return revision 1, followed by revision 2’s provision and credential write before the suspended save reaches `secrets.put`. That put unconditionally replaces the credential item with revision 1’s answer.

The later `answerInFlight` check correctly returns `staleAnswer`, but cannot undo the credential overwrite. Subsequent attempts load credentials without checking their revision, so revision 1’s base credentials can reach revision 2’s server.

This race pre-exists these fixes. The [new regression](native/Packages/TunnelEngine/Tests/TunnelEngineTests/Round4ControllerTests.swift:128) suspends before the second revision check, missing the remaining check/write window.

**Fix:** Make the payload-revision comparison and conditional credential write one atomic secret-store operation. Test provisioning after the final revision read has captured its result but before the old write executes.

**3. MEDIUM — Exhausted GUI deletion retries leave the hidden pause replayable. Incomplete fix for round-5 #5.**

[ConnectionStore.swift:2512](native/App/Stores/ConnectionStore.swift:2512), [ConnectionStore.swift:2527](native/App/Stores/ConnectionStore.swift:2527).

Same-user malware copies a genuine pause and removes its expiry. The GUI launches while keychain deletion is unavailable. After the initial attempt and five retries, consumption stops permanently for that run; launch reconciliation also unregisters the agent independently of consumption succeeding.

After keychain recovery, nothing retries the deletion. Quit, restore the genuine record and expiry within its validity window, and relaunch: its surviving nonce still verifies, allowing the signed app to arm/start the profile.

This is a remaining 2.0.2 pause-replay path. The [new GUI test](native/Tests/LockPlusTests/Round5FixTests.swift:85) restores keychain access after the first failed deletion.

**Fix:** Keep consumption owed until successful, with later recovery/load/wake retries, and defer agent unregistration while it is owed. Test exhaustion → keychain recovery → genuine-record restoration → relaunch, asserting no arm/start.
