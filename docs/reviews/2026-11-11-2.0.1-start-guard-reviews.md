# LockPlus 2.0.1 start guard: overview of the security reviews

Reviewed: the 2.0.1 start guard (`91a0c318`) and its ten rounds of fixes, up to `12552857`. This page is the index to the reports in `2026-11-11-fable-guard-*.md` and `2026-11-11-codex-guard-*.md`; the reports are published as written.

## The measured bug

Before the VM measurements (Phase 0, macOS 26.6.2 and 27.2), the assumption was that macOS runs one LockPlus configuration at a time. It does not: two configurations of the same app, started in either order, from the app, `scutil` or the System Settings toggle, both reach Connected in the same extension process. The tunnel that was started first then stops passing traffic (its WireGuard packets, keepalives included, stop at the moment the second one starts) while macOS and `scutil` keep showing it as Connected, and stopping the second one does not revive it. With the kill switch on, the first tunnel becomes a black hole rather than a leak (no probe packet left the Mac), but the user is cut off with no hint of the cause, and the second profile's traffic is blocked too.

2.0.1 adds a start guard in the extension: a start beside another live session is refused (error 222) instead of displacing it, a start with the kill switch outranks a session without it (that session ends visibly, error 223), and kill switch against kill switch is first-wins. The rules are in DESIGN §7.2 and §1.3 A2.

## Process

- Two independent model families reviewed every round, read-only: Fable (Anthropic) and, from round 2, OpenAI Codex (GPT-6-Astra at max reasoning effort). Round 1 also has a quick default-effort Codex pass, which found nothing; it is published for honesty, and it shows why the later passes ran at max effort.
- Every finding of every round was fixed or consciously accepted in writing (DESIGN §20 risk 27), including LOWs and nits. The reviewers re-checked the previous round's fixes each time, which is how fixes that introduced a new problem were caught.
- Stopping rule: stop when neither reviewer reports a HIGH and every remaining MEDIUM was already present in 2.0.0. Round 10 met it; a final spot check of the last commit found no HIGH and no MEDIUM.
- Besides the reviews, the build was run in the two VMs (`7b24776a` fixes the display findings of that run: refused starts take the hero, the 223 text in the detail, onboarding import), and the new code was checked by mutation: tests were required to fail when a guard condition was removed.

## Accepted residuals (DESIGN §20 risk 27)

- An NE instance abandoned without `stopTunnel` or `deinit` (unmeasured; the one candidate is an `nesessionmanager` crash or restart with the extension process surviving) leaves its session in the controller with nothing enforcing it, until the extension process exits. Starts it outranks are refused; a same-profile kill-switch restart waits (closed).
- A same-profile duplicate kill-switch start waits without a time limit beside a running kill-switch session: closed, but whether NE keeps the running session's traffic flowing beside an indefinitely pending start is unmeasured (a VM scenario is listed for it).
- A pending duplicate started outside LockPlus keeps the app busy (no saves, heals or on-demand restores) until it is stopped. The app names it in Diagnostics; the proper fix is to identify the NE configuration, planned for 2.0.2/2.1.
- A live protection flag that NE changes between the controller's last read and `cancelTunnelWithError` cannot be excluded from our side (NE offers no conditional cancel); it needs a concurrent flag save on that very session and the window is a few synchronous instructions.
- Pre-existing in 2.0.0, from the last two rounds: a metadata revision can be reused after a failed write across a relaunch (a same-user-unwritable high-water mark is a 2.1 item), and an automatic retry's manager mutation can land inside another start of the same user's own profile (availability, not a leak; scheduled for 2.0.2).
- The final LOW (a double-failure corner that fails closed) goes to 2.0.2.

## The coordinator's mistake in round 8

The round 7 fix `175a8999` made the app remember a skipped manager rollback in a durable `pendingRollbacks` record in `settings.json`, so that a rollback interrupted by a failed write would not be read as a replay of old metadata. Both reviewers flagged it in the next round (Fable M1, Codex HIGH 1): same-user code can write that file, so the record let it exempt an older, authentic metadata file from replay detection and downgrade the kill switch. The mistake was the coordinator's: it put a security-relevant marker in the one place that is easy to persist and that same-user code can write, which is the kind of choice the reviews exist to catch, and they did. It was reverted in `d46a0cb2`: the marker is in memory only, it is forgotten only on positive confirmation, and after a relaunch in that state the profile is quarantined like any replay (fail closed).
