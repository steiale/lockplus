# LockPlus 2.0.2: overview of the security reviews

Reviewed: everything that changed from 2.0.1 to the 2.0.2 release candidate (build 200026, `8df44088`), in seven rounds.
This page is the index to the reports in `2026-11-12-fable-2.0.2-r*.md`, `2026-11-12-codex-2.0.2-r*.md` and
`2026-11-12-sonnet-2.0.2-r1.md`; the reports are published as written, with only local paths shortened.

## What 2.0.2 changes

1. Profile checks and zip reading move out of the root tunnel component into a sandboxed, network-less helper
   (`LockPlusValidator.xpc`).
2. The tunnel component accepts only LockPlus builds at least as new as itself (a build floor in its peer requirement).
3. Owner-authorised starts: a start from System Settings or `scutil` is honoured only for the Auto-Connect profile;
   everything else is refused (error 225).
4. Open `.ovpn`, `.conf` and `.zip` from Finder and the Dock.
5. Test Connection.

## Process

- Two independent model families reviewed every round, read-only and adversarially, against the same threat model
  (other users on the Mac, malware running as you, a hostile network, a malicious profile file): Fable (Anthropic) and
  OpenAI Codex (GPT-6-Astra at max reasoning effort). Round 1 also had a Sonnet first pass for correctness, copy and
  test gaps. Codex reviewed a copy of the public source tree.
- Every finding of every round was fixed or written down as an accepted limit in DESIGN §20, LOWs and nits included.
  Each round re-checked the previous round's fixes; several new findings were caused by earlier fixes and were caught
  that way.
- Stopping rule: neither reviewer reports a HIGH, and what remains is documented.

## How it went

| Round | Fable | Codex | Notes |
|---|---|---|---|
| 1 | 1 HIGH, 3 MEDIUM | 1 HIGH, 6 MEDIUM | The HIGH (both): "Save Only" on a connected kill-switch profile could make macOS's restart of that session fail, leaving the Mac open. |
| 2 | 0 HIGH, 2 MEDIUM | 2 HIGH, 5 MEDIUM | Unsigned settings records could still lead to starts; two more ways to break a kill-switch restart. |
| 3 | 0 HIGH, 1 MEDIUM | 1 HIGH, 5 MEDIUM | A background install of a checked edit could cancel a restart in progress. |
| 4 | 0 HIGH, 0 MEDIUM | 2 HIGH, 2 MEDIUM | A "user stopped" notice added in round 3 could hit a newer session. |
| 5 | GO, 0 HIGH, 0 MEDIUM | 1 HIGH, 6 MEDIUM | The same notice again. Decision: remove the notice instead of patching it a third time. |
| 6 | GO | 0 HIGH, 3 MEDIUM | Narrow answer and credential races, a pause value that could survive a keychain failure. |
| 7 | GO | 0 HIGH, 2 MEDIUM | One MEDIUM accepted as a documented limit (below), the other fixed. |

The two families complemented each other: Codex was stricter and kept finding timing chains, Fable found the first HIGH
and judged the trade-offs. The round-5 decision is worth stating plainly: a mechanism added to close a LOW finding
caused a new HIGH in each of the next three rounds, so it was taken out, and the smaller original limit is documented.

## What the first release candidate's VM run found

The end-to-end run of the first release candidate (build 200026) on macOS 26 and 27 found two bugs that no review and no
unit test had caught, because both only show up in a signed build on a real system:

- the sandboxed profile checker crashed at every launch (it set its code-signing requirement on the service listener, an
  API that only works on other listener types), so imports stayed "Not yet verified";
- the background helper that ends a pause deadlocked, so a paused kill-switch profile never reconnected without the app.

Both were fixed, and the fixes went through three more short rounds (`2026-11-12-fable-2.0.2-rc-fix*.md`,
`2026-11-12-codex-2.0.2-rc-fix1.md`): the reviews found that the first fix could give up a resume after a slow run and that
the resume hand-off had to survive being cut off at any point. The release is build 200027. New tests now start the real
embedded checker and the helper's run loop, so this class of bug fails in the test suite next time.

## Accepted limits (DESIGN §20 risks 29–31)

- After you cancel or pause a kill-switch session that is already down (for example while it waits for a network), one
  start of that same profile from outside LockPlus can still be admitted until you disconnect it while it runs, delete
  the profile or restart the Mac. It uses your own server and saved credentials, never leaves the Mac open, and is less
  than 2.0.1 allowed (every outside start).
- If the keychain can't delete a pause's one-time value for a whole run, and a program running as you then writes back a
  complete older copy of LockPlus's settings file, that pause can resume once (your own profile, within 7 days). There
  is no full cure without storage the same user can't write.
- A lost or corrupted state file of the tunnel component, or a full permission table (256 entries), can make macOS's
  restart of a kill-switch session fail.

The reports' findings on the real system (macOS 26 and 27 VMs) were checked in the end-to-end run of the release
candidate; those logs are not published.

An AI review is not a human security audit. If you find something these passes missed, please report it privately
through GitHub's vulnerability reporting.
