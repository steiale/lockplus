### M1 is closed

- **One start site:** `managers.start` is called only at `HeadlessResume.swift:338`.
- **Two independent conditions in front of it:**
  - `alreadyActive` is read once (`:223`) and gates the intent branch (`:225`), the arm (`:269`) and the start (`:320`). A target that was active at the first look is never started by that run.
  - `guard intentHolds` (`:333`) sits directly before the start. `intentHolds` is set only at `:242`, on `.holds`.
- **Forged record:** if the target is inactive, the intent check fails, `target` becomes nil and neither the arm nor the start is reached. If the target is active, both are skipped.
- **Legacy extension, kill-switch profile:** every start now passes the arm branch, so the `.legacyExtension` refusal (`:281`) applies. The only way past it is the arm-failure fallback, which needs a genuine intent (see L2).
- **Status re-read at `:228`:** if it differs from `:223`, the run returns `.targetInTransition`; both outcomes are safe.
- **Tests:** `aTargetThatStopsDuringTheRunIsNotStartedWithoutAnIntentCheck` (forged, kill switch, legacy extension, `.connected` to `.disconnected` during the save) fails if the start gate reads the live status again: the outcome becomes `.resumed(restarted: nil)` and the value is spent. `aForgedRecordNamingAConnectingProfileStartsNothing` is the test I asked for.

### Your two questions on `.targetInTransition`

- **Can it keep a genuine pause pending forever?** Yes, as long as the target is `.connecting` or `.disconnecting` at each minute's look. There is no bound, not even the 7 days, because the return at `:229` comes before the intent check. See L1.
- **Can same-user code use that to deny a resume, and is it worse than before?** Yes, by looping `scutil --nc start P`. It is not worse:
  - holding `instance.lock` already kept a pause pending, more reliably;
  - at c380a19b the same trick ended the pause for good, silently. Now each run logs `targetInTransition(connecting)`, nothing is spent, and the resume happens as soon as the loop stops.

## MEDIUM

**M1. The retry window counts from `pausedUntil`, so the first run after a longer sleep gets no retry.** `HeadlessResume.swift:268`, `:272-273`, `:329-330`.

- **Cause:** `outOfTimeEnds = now - until >= 600 s`. The agent does not run while the Mac sleeps or is shut down. If the Mac wakes more than 10 minutes after the pause ended, the first run is already past the window.
- **Scenario:** pause a manual profile for an hour, quit LockPlus, close the lid for two hours. On wake the coalesced run is slow and runs out of time at the arm or the settle.
- **Result:** the terminal path. No start, the value is spent, the pause is cleared, the agent unregisters. The profile (kill switch included) stays down with no retry and no Problems line.
- **Why MEDIUM:** this is M1 of my first fix review (`fable-fix.md`), which named "the coalesced run right after wake" as the typical slow run. 5e7edf83 fixed it; this hunk undoes that fix for every sleep longer than 10 minutes past the pause's end. How often the post-wake run is slow is still unmeasured.
- **My part:** review 2 L3 proposed "about 10 minutes past `pausedUntil`". That anchor was wrong.
- **Pinned by tests:** `outOfTimeRetriesEndAfterTheRetryWindow` (11-minute case) and `noTimeToArmPastTheRetryWindowEndsThePause` assert this behaviour on a first run.
- **Fix, either of:**
  - **Remove the window for 2.0.2** (recommended for the RC): drop `outOfTimeRetryWindow` and `outOfTimeEnds`, delete the two tests' terminal cases, floor back to 869 or 870. L3 returns as a documented LOW (bounded by the 7-day intent age), to be done properly in 2.1.
  - **Anchor it at the first out-of-time run:** write a `resumeRetrySince` date to settings.json on the first `.outOfTime` return, count the 10 minutes from there, clear it in the final write. Treat a future date as "now". Forging it gains nothing: a past date only denies a resume, a later one only prolongs a retry, and same-user code can do both already.
- **Re-check needed:** that hunk only.

## LOW

**L1. `.targetInTransition` has no bound.** `HeadlessResume.swift:229`, `:238`, `:321`.

- **Without an attacker:** a cut-off run's start that never establishes (an OpenVPN profile retrying an unreachable server stays `.connecting`) keeps the pause record, the unspent value and the every-minute agent until the session connects, fails, or the GUI runs. The other profiles' on-demand is off during that time, which is the designed state while the target comes up.
- **With one:** see the answer above; not worse than the lock.
- **Fix (2.1, together with the window):** past the same first-seen anchor, take the terminal path. Do not anchor it at `pausedUntil` (M1).

**L2. The arm-failure fallback trusts a field the intent does not cover.** `HeadlessResume.swift:285-286`. Not from this diff; you asked for a judgement.

- **Cause:** the HMAC covers the profile ID and the pause's end (`AppSettings.swift:119`), not `onDemandEnabledIDs`. Same-user code can add the target to that list in a genuine record. An arm `.failed` then starts with `crashRestart` (no `lp.manual`) instead of returning `.armUnavailable`.
- **Forged record:** cannot reach it. `target` is nil, or the target is active and the arm branch is skipped.
- **On the 200027 extension:** no start is gained. The extension admits a non-manual start by its own `providerConfiguration["onDemand"]` (`StartRequest.swift:86`), which only the owner's app writes. For a manual profile it refuses. The run still spends the value and logs `resumed(restarted: P)`: a denial, which same-user code has cheaper ways to get.
- **On a legacy extension with a kill-switch profile:** the start is admitted, and the `.legacyExtension` refusal is not applied. It needs all of: a genuine pause of that profile, the edited list, and an arm that fails without a hello (a timeout, e.g. by SIGSTOPping the agent; racy). What it yields is the user's own verified profile started, as they asked, with the round-2 L6 defect: NE's restart into the replacement extension arrives without options and is refused. The attacker gains no start they choose, and "profile down" is available to them anyway.
- **Genuine on-demand profile, no attacker:** the fallback is correct. The replacement extension admits the restart by its on-demand flag.
- **Fix (small, can wait for 2.1):** decide the fallback from the manager's stored `onDemand` (`ManagerConfiguration.Stored.onDemand`, the value the extension reads) instead of the record's list. Agent and extension then agree by construction, and the list stops being an input to a start decision.
