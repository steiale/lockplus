## MEDIUM

**M1. The target's status is read three times; a forged record reaches `managers.start` with no intent check.** `native/App/Headless/HeadlessResume.swift:205`, `:236`, `:279`, `:288`.

- **Cause:** the new shortcut at 205 skips `checkResumeIntent` when the target is active. Lines 236 and 279 read the live `connection.status` again (`ManagerStore.swift:393`), after awaits. If the target was active at 205 and is not at 279, the run goes on to `verifyForStart` and `managers.start` with a record nobody verified.
- **Scenario:** same-user code, GUI not running, no pause needed.
  1. Write `pausedUntil` in the past and `pausedState { profileID: P, onDemandEnabledIDs: [P], intent: anything }` to settings.json.
  2. Loop `scutil --nc start P`. The extension refuses it, but NE reports `.connecting` meanwhile.
  3. Run `LockPlus --resume-protection`. At 205 P is `.connecting`: no intent check. At 236 it is still active: no arm. The `setOnDemandEnabled` await at 272 suspends; the refused start ends. At 279 P is inactive: `prepareForStart`, settle, then `managers.start(P, [lp.manual: 1])`.
- **Result on the 200027 extension:** refused, because the options carry no nonce (`StartAuthorisation.swift:107`). The run still spends a genuine pause's value, clears the pause and logs `resumed(restarted: P)`.
- **Result on a legacy extension (no `startAuthorisation` capability):** the start is admitted. The kill-switch refusal for legacy extensions sits in the arm branch, which was skipped, so this includes kill-switch profiles. It needs no one-time value, so it repeats at will. This is the `armStart`-proxy case round 1 (Codex 3) closed.
- **Unverified assumption:** nothing between 205 and 236 awaits, so I assume the status cannot flip there. If it can (NE updating `status` off the main queue), the run arms and the 200027 extension admits the start too.
- **Same bug without an attacker:** a cut-off run's start fails while the next run is between 205 and 279. That run issues a start without a nonce, is refused, spends and ends the pause. The "resumes once more" promise does not hold there.
- **Fix:** decide once, and make the start depend on the check.
  - `let alreadyActive = target.map { managers.status($0).isActive } ?? false`, used at 205, 236 and 279.
  - A `var intentHolds = false`, set only on `.holds`; `guard intentHolds` directly before `managers.start`.
  - If `alreadyActive` and the target is no longer active at 279: return a retry outcome, nothing spent. The next run does the intent check.
- **Test:** a fake manager whose status goes from `.connecting` to `.disconnected` inside `setOnDemandEnabled`, with a forged record. Expect no start, no arm, value unspent.

## LOW

**L1. A genuine record can start its profile more than once.** `HeadlessResume.swift:288-291`.

- **Scenario:** same-user code kills the agent between `managers.start` and `spend()` (SIGSTOP stepping while polling `scutil --nc status`). The value stays. It then holds `instance.lock` so no run completes the hand-off. After the user disconnects P, it releases the lock and runs the agent: the record verifies, P is armed and started again. Each won race gives one more start, for up to 7 days (`ResumeIntent.isFresh`) or until the GUI runs.
- **Assessment:** this is the price of spending after the start, and that order is right: losing the restart of a kill-switch profile is worse than repeating a start of the owner's own verified profile. The race is sub-millisecond and one loss ends it.
- **Fix:** document it as a known limit for 2.0.2. For 2.1, replace the value before the start with a sealed "start issued at T" marker that allows a re-issue only for a few minutes.

**L2. Any active status counts as "an earlier run started it", silently.** `HeadlessResume.swift:205-207`; `isActive` includes `.connecting` (`ConnectionStore.swift:2790`).

- **Scenario:** during the agent's tick, `scutil --nc start P` puts a manual P in `.connecting` for a moment. The run spends the genuine value, clears the pause, unregisters and logs `resumed(restarted: P)`. The extension then refuses the start and P stays down.
- **What is new:** not the denial (a tampered record or a held lock already did that), but that it leaves no fault line. A forged record naming an active profile also passes without the "pause record without a valid intent" fault.
- **Your question, answered:** apart from M1, a forged record gets nothing through this path that it did not get before: no arm, no start, the target's on-demand restored as before.
- **Fix:** in the active path run `checkResumeIntent` for the log only, and log a fault when it does not hold. Spend only on `.connected` or `.reasserting`; on `.connecting` return a retry outcome and let the next run look again.

**L3. Out-of-time retries have no bound short of 7 days.** `HeadlessResume.swift:238`, `:285`.

- **Scenario:** every run ends `.outOfTime` (a configuration that never settles within 2 s, or a machine where load and arm always take over 4 s). Each minute's run arms, saves and returns. The manual kill-switch target stays down, and the other profiles' on-demand stays off, where the old terminal path restored it at once. It ends only when the intent is too old.
- **Attacker angle:** nothing new. Holding `instance.lock` already keeps a pause pending. Repeated arms are harmless: 15 s lifetime, one per profile, the nonce never leaves the agent, and a non-manual start never consumes an arm.
- **Fix:** after about 10 minutes past `pausedUntil`, take the terminal path (restore everything, end the pause).

## NIT

- **N1. Temp-file sweep: safe, one test missing.** `AppDataStore.swift:179-191`. `lstat` requires a regular file and `unlink` never follows a link, so a swap between the two removes only the link. The name must be `.<name>.<UUID>.tmp` and older than 60 s. If the data directory itself is replaced by a symlink, the sweep deletes files of that exact shape in the target, which same-user code can delete anyway. Add a symlink named like a temp file to `orphanTempFilesAreSweptAndNothingElse` and assert the link and its target survive.
- **N2. Hold record: no replay, one spurious fault.** `HeadlessResume.swift:309-316`. The record now survives every early return together with its setting, which is consistent. A cut between the consume at 309 and the write at 316 leaves the setting without its value; the GUI then logs "doesn't verify; dropped". Harmless. A failed consume is still not tracked as owed (as before this diff).
- **N3. Test gaps.** No test changes the status during a run (M1), names an active profile in a forged record, or covers `.disconnecting`. By reading, the existing tests do catch the two main regressions: spending before the start fails `stoppedDuringTheStartTheNextRunCompletesOrResumesOnce` (line 227), and removing the active shortcut fails `anActiveTargetIsTakenAsRestarted`.
