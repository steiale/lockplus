# LockPlus 2.0.2 security review (Fable, round 1)

Scope: `git diff release-2.0.1..HEAD` (21 commits, HEAD f1ae738e), read-only. Nothing was built or run; every finding is from reading the code, the plan and DESIGN draft 10.4. NE behaviour is taken from the project's own measurements (S2, E2E-4), not re-measured.

Paths are relative to `native/` unless they start with `docs/`.

## Verdict

One HIGH, three MEDIUM, eight LOW, five NIT. The HIGH is the plan's own stop condition for item 3: NE's restart of a live kill-switch session can be refused with 225, which leaves the Mac open.

The validator boundary, the build floor and the arm/nonce binding hold against the stated threat model. I found no way to turn a crash or timeout into "accepted", no way for another uid or same-user code to arm or forge a start, and no save without a Confirm (but see L2 on how that Confirm can be obtained).

## HIGH

### H1. NE's restart of a live kill-switch session is refused after the session's authorising state changes (new in 2.0.2)

The restart of a running session is authorised by state that can change while the session is live. Two variants, same outcome.

**Variant a: "Save Only" on a connected profile.**
- `Packages/TunnelEngine/Sources/TunnelEngine/Controller/TunnelController.swift:1772`: `profileProvisioned` calls `clearAuthorisation(key)` on every higher-revision provision.
- `payloadCommitted` only ends a start that is still waiting before Connected; a connected session keeps running.
- `App/Services/AppEditorBackend.swift:56-58`: `replacePayload` provisions the new revision, and the session is restarted only for `.saveAndReconnect`.
- `App/UI/Editor/EditorWindow.swift:122-130`: the editor offers "Save Only" while connected.
- Scenario: the user connects a kill-switch profile from LockPlus (armed, nonce N recorded), edits it and picks Save Only. The session stays up with no authorisation record. When NE later restarts it (provider crash, or the E2E-4 no-network restart), it replays `lp.manual=1` + N. `StartAuthorisation.swift:66` finds no record, so the start is refused with 225.
- A failed `includeAllNetworks` start is open (E14c). The app then shows "started outside LockPlus", which is wrong.
- In 2.0.1 the same restart was accepted (`runStarting` accepts a configuration older than the payload).
- `docs/native/DESIGN.md:2471` accepts this as a residual because "the app restarts the session after an edit, so the window is small". That premise is false for Save Only: the window lasts until the user disconnects.
- `StartAuthorisationTests.swift:202-211` (`higherRevisionClearsAuthorisationButASameRevisionRetryKeepsIt`) asserts the clearing on a connected session, so the suite locks the behaviour in.

**Variant b: an unattended session whose on-demand rules go away while it is connected.**
- `StartAuthorisation.swift:60`: a non-manual start is admitted only while `cfg.hasOnDemandRules` is true at that moment. Nothing is recorded for an unattended admission.
- `App/Model/ManagerConfiguration.swift:114`: `providerConfiguration.onDemand` mirrors `onDemandPlan != nil`.
- `App/Stores/ProfilesStore.swift:681-699`: `resaveOnDemand` saves the connected profile's manager when its plan changes.
- The plan becomes nil when the user picks another Auto-Connect profile or none, turns off Stay Connected, or removes the saved password.
- Scenario: a kill-switch auto-connect profile was connected by on-demand (nil options). The user changes the Auto-Connect profile while connected; the session stays up (S2 E9). `CrashRestartPolicy` then answers `.expectSystemRestart`, NE restarts with nil options, `hasOnDemandRules` is now false, and the start is refused with 225. Open.
- Confidence: the code path is confirmed by reading. That NE restarts by itself in this state is the project's own S2 E1 / E2E-4 result. Confirm on the VM.

**Fix.**
- Tie the authorisation to the session, not to the revision or the current rules.
- Do not clear on a higher-revision provision while that key's session is live or awaiting NE's restart. Simplest: do not clear on provision at all. The nonce is bound to the key, only NE and the owner's app hold it, and a user stop still clears it.
- Record unattended admissions too (for example `AuthorisedStart` with a nil nonce) and honour a non-manual restart of that key until a user stop, removal or wipe clears it.
- For any `includeAllNetworks` start that looks like a restart of a session this extension admitted, prefer admit over 225.
- Tests: an engine test for "armed, connected, higher revision, new controller, replay admitted"; one for "unattended, connected, `onDemand` false, restart admitted"; an app test for Save Only. Add both variants to the E2E-8 S list.

## MEDIUM

### M1. A slow validator is recorded as "this file crashed the check", permanently in two places (new in 2.0.2)

This is the open point from the Phase 2 report, and it is wider than described there. It fails closed, so it is an availability bug, not a bypass.

- `App/Services/ServiceProfileValidator.swift:22` maps every `.timeout` to `rejected("check crashed")`.
- `Packages/LockPlusCore/Sources/LPXPCClient/ValidatorClient.swift:190-191`: a `hello` timeout (3 s) is also `.timeout`, and `call()` lets it through. So a slow first service launch is treated as a hostile file before any byte of it was evaluated. A cold launch of an XPC service that links openvpn3 and OpenSSL, right after install, is when this is most likely.
- `ValidatorClient.swift:124-125`: a timeout does not reset the connection, and the service's watchdog is 10 s against the client's 8 s (`ValidatorServiceHandler.swift:14`). The next file's 8 s clock runs while the service is still busy with the previous one, so one slow entry in a zip can take the following entries with it.

Consequences:
- Import: the file is shown as "LockPlus couldn't check this file safely" and can't be saved. A retry fixes it.
- `App/Stores/ProfilesStore.swift:884-903` (`verifyPending`): a timeout writes `.checkCrashed` into the saved profile's report, and `alreadyRejected` then skips it forever. A good "Not yet verified" profile becomes permanently unconnectable until it is re-imported.
- `App/Stores/GoAppMigrator.swift:421`: `draft` returns nil, so a tunnel is dropped from the Go-app migration on the first launch.

Fix:
- Only a second interruption on the same request (`.profileCheckCrashed`) is a refusal.
- Map a `hello` timeout to "unavailable" (throw, so the profile is saved as not yet verified).
- Treat an `evaluateProfile` timeout as a refusal only after one retry on a fresh process: drop the connection on timeout so the wedged request can't eat the next one's budget.
- Never persist `.checkCrashed` from `verifyPending` or the migrator on a timeout.
- Make the client timeout longer than the watchdog, or the watchdog shorter than the client timeout, so the service's own exit is what the client sees.
- Tests: `ValidatorClientTests` for a hello timeout and for a timeout followed by an innocent request; a `verifyPending` test that a timeout leaves the profile retryable.

### M2. Self-test shows IPv6 as "Blocked, nothing leaves outside the tunnel" (green) on any prompt failure (new in 2.0.2)

- `App/Services/ConnectionSelfTest.swift:130-133`: for a full tunnel without tunnelled IPv6 and with the kill switch or `blockIPv6`, any v6 attempt that fails without timing out is `.blocked`. That is a pass glyph, and `overall` stays `.ok`.
- `handle` (lines 367-371) turns every `.failed` and `.waiting` into the same prompt failure: no AAAA or a DNS failure, a TLS failure, ECONNREFUSED, an RST, EHOSTUNREACH from the LAN router.
- Scenario: `blockIPv6WithoutKillSwitch` is on and the block is not effective. The v6 SYN leaves on en0 and the network answers with an RST or ICMP unreachable. A hostile network can do this on purpose, and networks with broken IPv6 do it by themselves. The row says "Blocked, nothing leaves outside the tunnel" although a packet just left outside the tunnel.
- I did not verify how `blockIPv6` is implemented. If it uses `::/1` routes into the utun, a working block times out (inconclusive), so a prompt failure is more likely to be one of the cases above than a real block.

Fix:
- Claim `.blocked` only for a local refusal: the path is unsatisfied with no usable v6 interface, or the error is ENETUNREACH/EHOSTUNREACH and a route lookup for the probe's v6 address resolves to the tunnel or a reject route.
- DNS failures are `.unreachable`.
- ECONNREFUSED, ECONNRESET and TLS errors mean packets left: report `.outsideTunnel` if the local address is not the tunnel's, else `.unreachable`.
- Tests: one `classify` case per error class.

### M3. Self-test's "Through the tunnel" is decided by source-address equality, not by the interface the connection used (new in 2.0.2)

- `ConnectionSelfTest.swift:112-118`: `sourceIsTunnel || interfaceIsTunnel`.
- Line 387: `fetch.interface` is `RouteProbe.interface(owningAddress: local)`, a getifaddrs lookup by address, not the connection's `NWPath` interface.
- Lines 187-189: `facts.tunnelInterface` is found the same way, from addresses that include the profile's static ones (line 218).
- Scenario: the LAN hands out the tunnel's inner address (10.8.0.2 is OpenVPN's default first client address; a WireGuard `Address` is static and may be known to an attacker). Then en0 and utunN own the same address. A probe that leaves by en0 has a "tunnel" source, and the address lookup can name en0 as the tunnel interface. The row reads "Through the tunnel (en0, from 10.8.0.2)".
- For harm, the default route must also not be the tunnel, which is the failure the test exists to catch. I rate it MEDIUM because it is a false green in the security check under the hostile-network model; LOW is arguable.

Fix:
- Take the interface from `conn.currentPath` (`availableInterfaces.first`, or the path's `localEndpoint` interface).
- Require that it is a utun and equals the session's interface. Source equality is supporting evidence, never sufficient alone.
- If more than one interface owns a tunnel address, the verdict is inconclusive.
- Longer term, the extension should report its utun name in the snapshot.

## LOW

### L1. An unverified profile can be provisioned and started through the 221-retry path
- `App/Stores/ConnectionStore.swift:1087-1104`: after `.profileNotProvisioned` or `.profileRevisionStale`, the app calls `profiles.provision(p)` and `startNow` with no `engineVerified` check. Every other provision site has the gate (`ProfilesStore.swift:478, 508, 844`; `ConnectionStore.swift:1233`).
- Scenario: a profile is saved as "Not yet verified" (validator unavailable, for example `versionMismatch` after a brew upgrade under the running app). It has on-demand rules. NE starts it, the extension answers "not provisioned", the app provisions the unverified payload, and the start runs openvpn3's option parser and `eval_config` in root on bytes the sandbox never saw.
- The code predates 2.0.2, but its meaning is new: in 2.0.1 provision ran [6]/[7] itself.
- Fix: `guard p.engineVerified` inside `ProfilesStore.provision` (one place for every caller) and in this branch. Also return nil from `onDemandPlan` for an unverified profile.

### L2. Open-document import sheets can be confirmed by a stray Return, or swapped under the user (new in 2.0.2)
- `App/Services/OpenDocumentRouter.swift:64-78` activates the app and opens the sheet for any `open -a LockPlus f.ovpn`.
- `App/UI/Sheets/ImportSheets.swift:111-112, 265-266`: Import and Import Selected are `.defaultAction`.
- `App/Stores/ImportCoordinator.swift:160, 230-246`: a second open event replaces `model.preview` / `model.batch` while a sheet is up.
- Scenario: same-user malware fires the open while the user is typing, or just before the user clicks Import on their own file. The attacker's profile is saved and provisioned, named by the attacker, and selected. The attacker's file must still pass validation, and nothing is started.
- Fix: for imports that came from an open event, no default button (or enable Import after about 1 s); while a preview or batch is shown or an analysis is running, queue new events instead of replacing; name the source path in the sheet.

### L3. Opened paths are read synchronously on the main actor with a blocking `open(2)` (new exposure in 2.0.2)
- `App/Stores/AppDataStore.swift:122-123`: `AtomicFile.readResult` opens with `O_RDONLY | O_CLOEXEC` only. The safer `readNoFollow` (O_NONBLOCK, S_IFREG check) exists at line 98 and is not used here.
- `ImportCoordinator.swift:160-207` runs it in a `@MainActor` task.
- Scenario: `mkfifo x.ovpn; open -a LockPlus x.ovpn`, or a file on a stalled network mount. The UI hangs, including Disconnect.
- Fix: read off the main actor with `O_NONBLOCK`, `fstat` must say S_IFREG, and check the size cap before reading.

### L4. A 2.0.1 session that survives into the 2.0.2 extension may be refused on NE's restart (new in 2.0.2, unverified)
- `App/Model/ManagerConfiguration.swift:233, 260` and `ConnectionStore.swift:1394`: while the 2.0.1 extension is still active (replacement not yet approved), the app starts without a nonce.
- If the user approves the replacement while that kill-switch session runs and NE restarts it into the 2.0.2 extension, the replayed options are manual without a nonce, so 225 and open.
- Plan §3.3 relies on the quiesce stopping sessions, but this start happens after the quiesce. I did not trace whether a start is blocked during `extensionHandOver`.
- Fix: refuse app starts while an update is pending approval, or confirm in E2E-8 that the hand-over stops the session as a user stop.

### L5. The 256-entry cap can evict the running session's record
- `TunnelController.swift:1315-1322`: the oldest record by `at` goes, and a long-running session is the oldest. Records of sessions that ended for any reason but a user stop are kept forever (`:1303`), so they accumulate.
- Reaching 256 keys needs many profiles across uids. Another user can only get starts admitted while yours is not live, and can stop your session anyway. Impact is low.
- Fix: never evict the live session's key; drop the record when a session without `includeAllNetworks` ends (NE never restarts those). That also shrinks the replay surface.

### L6. A sandboxed exploit can approve its own file (design residual, not a regression)
- Plan §1.9 item 4 asks what is lost. A payload that gets code execution in the validator (not just a crash) can answer "valid" for itself. The app saves and provisions it, and root's openvpn3 parses the same bytes at start (`Tunnel/PayloadValidation.swift:56`, then the session's `eval_config`).
- 2.0.2 removes crashes, hangs and rejected input from root. It does not remove a reliable exploit, which gets a second attempt in root.
- No fix inside this design. Say it in DESIGN §20 so the claim stays honest. A fresh validator process per file would at least stop file A's exploit from approving file B.

### L7. A failed `state.plist` write is silent, and a lost record means a refused restart
- `Packages/TunnelEngine/Sources/TunnelEngine/Controller/TunnelStateStore.swift:91-101`: a save error is only logged.
- After a failed save of the authorisation (disk full) or a file discarded on a schema mismatch (`:85-88`), NE's replay of a kill-switch session is refused.
- Fix: covered by H1's rule (admit a restart of an `includeAllNetworks` session this extension admitted). At least log a fault with the consequence.

### L8. Not covered on the VM: a nil-option start after an armed session ended without a user stop
- The record survives `providerFailed`, `noNetwork` and `superseded`. If nesessionmanager ever reuses a session's last start options for a later System Settings or `scutil` start, that start would be a `.replay`.
- I have no evidence that it does; S2 E1 only measured the crash restart.
- Add to E2E-8 S: an armed session ended by a server-side failure, then `scutil --nc start`, must give 225.

## NIT

- **N1.** `Packages/LockPlusCore/Sources/LPWire/ValidatorWire.swift:116-129`: `isSafePath` accepts `a/b.ovpn`. The service sends leaf names only, so the wire rule should refuse `/`.
- **N2.** `Packages/LockPlusCore/Sources/LPWire/RequestReplies.swift:281-283`: `ValidateProfileReply` has no length caps for `staticChallenge`, `rejectedCategory` and `error.detail` beyond the 64 KiB reply cap. They are shown in the UI and written into metadata.
- **N3.** `VALIDATOR_REQ` has no build floor. The hello's build equality is self-reported, which is fine against an old genuine binary. Add the floor once a second validator build exists.
- **N4.** `Tools/release/verify.sh:192`: the previous-release floor check is skipped with a note when `LP_PREV_APP` is unset. Make it mandatory for a release run. It is the only check of the floor on real Developer ID signatures.
- **N5.** `LPEngineCheck` links `OpenVPNEngineCheck.evaluate` into the extension; only lint keeps `Tunnel/` from calling it. Move `ShimOptionsParser` into its own target so the extension can't link [7] at all.

Not a finding: images refused by file extension only (`ImportCoordinator.swift:173`). A PNG named `.ovpn` is parsed as text and rejected by [1]-[5].

## Focus points a–g

**a. Untrusted profile reaching openvpn3 in root; fixed point vs validator.**
- Provision is Swift-only (`PayloadValidation.swift:41-48`); `validateProfile` answers busy without decoding.
- The start runs [6] and `eval_config` in root on the stored bytes. The only way I found for bytes the sandbox never checked to get there is L1.
- The app stores exactly the text it sent to the validator, so there is no TOCTOU between check and save.
- The fixed-point check is sound as a stand-in for [6] at provision, because [6] still runs at start before the engine.
- A compromised signed app loses nothing against 2.0.1: it could always provision anything that passes root's own checks.

**b. Sandbox boundary.**
- Entitlements are exactly app-sandbox, enforced in three places (sources, golden, signed binary). Hardened runtime, no get-task-allow.
- The listener requires `APP_REQ`; the client requires `VALIDATOR_REQ` before `activate()`.
- Replies are capped before decode and range-checked.
- A crash is "retry once, then refuse"; a timeout is a refusal; nothing is "verified" without a reply. That is correct for security and too strict for availability (M1).
- A compromised service can approve files (L6). It cannot make the app write a path, and it cannot reach the network or the keychain.

**c. Build floor.**
- The string is right: quoted, numeric comparison, before the team clause.
- I did not test dynamic evaluation. `info[...]` on a running peer is evaluated against the on-disk Info.plist, which the CodeDirectory's special slot binds, and the dynamic check compares the running cdhash with the disk's. So an old signed app with an edited plist, or with a swapped embedded extension, should fail.
- Only a VM run with a real 200025 app against the 200026 extension proves this (E2E-8 R). The repo tests are static and ad hoc (`RequirementTests.floorComparesNumerically`).
- "Floor = own build" is right for Reinstall (same bundle).
- brew upgrade under a running app fails closed: the cdhash no longer matches the disk.

**d. Start authorisation.**
- The uid binding, the one-use arm, "a wrong guess burns nothing", refusal before the guard and before any secret read, and the 8-per-owner cap are correct and tested.
- The nonce is never logged or put on the XPC surface.
- Another user's or same-user code cannot arm.
- The defect is on the other side: legitimate NE restarts are refused (H1, L4, L7).

**e. Open documents.**
- Nothing is saved without Confirm.
- Zips go through the service.
- Names never become paths.
- 20 files per event.
- Weak points: how the Confirm can be obtained (L2) and the blocking read (L3).

**f. Self-test.**
- Runs only from the three buttons and ⌘R, and only while connected.
- One host, TLS with default trust, exact body, proxies off. A captive portal can't produce green.
- Copy Results leaves the server address out, and the bundle text goes through the Redactor.
- Two false-green paths: M2 and M3.

**g. Would the tests catch regressions?**
- Start-authorisation table: yes, the unit coverage is good. But one test asserts H1a as intended behaviour, and there is no test for a restart after an edit or after an on-demand change.
- Nothing in the repo exercises real NE replay. E2E-8 S6–S10 are the only guard and are still to run.
- Validator client: crash and retry are covered. Hello timeout, timeout followed by an innocent request, and `verifyPending` persistence are not (M1).
- The `engineVerified` gate has no test on the retry path (L1).
- Self-test: `classify` is covered for the designed cases; there is no case for an address collision or for RST/DNS failure on v6.
- Open documents: the router's pure logic is covered; sheet replacement, the default button and non-regular files are not.
- Fixed point: the corpus test is good.
