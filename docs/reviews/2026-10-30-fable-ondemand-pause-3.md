## 2. Findings, most severe first

**N1 HIGH — a stale `.disconnected` of the previous session clears `starting` mid-window; the restore then lands inside X's own pending start and X starts with A on.** CS:144 (`clearStarting(id)` unconditional for every status), CS:191, CS:206, CS:420-436.
Scenario: X connected, A paused (record [A]). User clicks Disconnect → X `.disconnecting`; within NE's ~1 s stop the user clicks Connect again. `connect(X)` (CS:347-363): `.disconnecting` is not `isActive`, so `startNow(X)` runs at once (S2 already says a start issued while NE is Stopping is dropped — today this reconnect silently fails until F9). NE then reports X `.disconnected` → `handle`: `clearStarting(X)` → `observedDisconnect` → user stop → `restoreIfIdle()` (CS:206, and again CS:191) → `othersBusy(except: A)` false (nothing starting, active or awaiting) → `saveOnDemand(A)` = A ON, record cleared. The `startNow` Task is not `gone()` (token unchanged); if it is in `waitUntilSettled` the restore save merely extends the settle; the F6 re-check (CS:430) sees no *active* profile → `managers.start(X)` beside A enabled → the E2E-3 state on the next en0 change. Nothing re-pauses A (`pauseOtherOnDemand` ran before), the pane shows nothing (A not recorded, A on). The R7 comment (CS:394) names exactly this arrival but protects only the token.
Fix: (a) add `issued: Set<UUID>` set right before `managers.start` (CS:436 and the `.restart` branch CS:915); in `handle()` clear `starting` on a non-active status only if `issued.contains(id)` (an active status always clears). (b) In `connect()`, treat `statuses[id] == .disconnecting` like a switch of the same profile: `pendingSwitch = id; return`, and let `handle(.disconnected)` (CS:181-184) start it — this also fixes the S2 silent drop for same-profile reconnects. Test: X `.disconnecting`, `connect(X)`, emit `.disconnected` inside the settle hook, assert `onDemandAtStart.last` excludes A.

**N2 HIGH — the R2 widened restore set re-enables on-demand during an extension update/reinstall quiesce.** CS:526-534 (`wantsRestore` ignores `pendingResume`), CS:191, PS:314-320, MQ:24-42.
Scenario: §12.3 update: `quiesce` writes `pendingResume`, `setOnDemandEnabled(false)` for A, `managers.stop(X)` and waits ≤ 15 s for `.disconnected`. That `.disconnected` → `observedDisconnect` (not a `userStops` entry: MQ calls `managers.stop` directly) → fetch → not a fresh crash → `clearAwaiting` + `restoreIfIdle` (CS:262-263) → `wantsRestore(A)`: plan enabled (not paused/suspended/held), manager off → **A saved with on-demand ON while the extension is being replaced**, the exact state `quiesce` exists to prevent (NE may on-demand-start A against the old/replaced extension; a reinstall then deactivates under a live start). Before R2 only the record was restored and `quiesce` never writes the record. The same hole lets `load()`'s drift heal (`syncManager(A)`, PS:152, plan enabled) turn A on during the quiesce when nothing is active.
Fix: fold `settings.value.pendingResume != nil || expectedUpdate != nil` into `onDemandPlan`'s `paused` (PS:318) so `wantsRestore`, `saveOnDemand`, `syncManager` and `resaveOnDemand` all hold off until `resumeAfterUpdate` hands back through the record. Test: `quiesce(.extensionUpdate)` with A on and X connected, emit X `.disconnected`, assert A off and `pendingResume` intact.

**N3 MEDIUM — the U7 exemption saves a manager inside its OWN pending start (`.connecting` counts as running).** CS:503-505 (`isActive`), PS:170, PS:143/152, PS:428.

A's manager drifted (nehelper rewrite is routine on 26/27) → `mutationsBlocked(A)`: `mutationsDeferred()` true, `runningProfileMayMutate(A)`: `statuses[A] == .connecting` → active, `othersBusy(except: A)` false → **exempt** → `syncManager(A)` saves A's flags while A's kill-switch start is pending. Also note the exemption heals **flags** on a connected manager, which DESIGN:3043 says "stay disconnected-only (L-KS-2)" and `updatePolicy` (PS:393-399) refuses; E9 covered rules/isOnDemandEnabled/name only (U7 below). **N4 MEDIUM — R11 still open for an in-flight async write.** SS:32-40, ADS:162-166.

## 4. Simplifications (no behaviour change)
1. **One pending map replaces five fields.** `starting`, `startWatch`, `awaitingRestart`, `awaitingWatch`, `startToken` → `pending: [UUID: Pending]` with `enum Pending { case starting(token: UInt64, issued: Bool), awaitingRestart }` plus one `watch: Task` per entry and one `arm(id, timeout) { clearPending(id); restoreIfIdle() }` (the F9 timer and the R1 fallback are the same timer with the same action; the token bump becomes "my entry is gone"). `othersBusy` = `pending.keys.contains { $0 != id } || pendingSwitch… || active…`. `gone()` = `pending[id] != .starting(token, _)`. This also gives N1's `issued` a home.
2. **`restoring` derived.** Make `restoreTask` the observed property and `restoring` a computed `restoreTask != nil` (or keep one stored flag and drop the other); `restoreAgain` stays.
3. **One closure into `ProfilesStore`.** `mutationsDeferred` + `runningProfileMayMutate` → `mutationBlocked: (UUID) -> Bool` wired to `connection.mutationBlocked(id)` = `isBusy && !mayMutateRunning(id)`; `mutationsBlocked(for:)` (PS:170) disappears. The headless store sets `{ _ in true }`.
4. **`fetchLastDisconnectErrorBounded` = `withDeadline`** (LPModel/OneShot.swift:61) — the code re-implements it; `await withDeadline(disconnectErrorTimeout, onTimeout: .init(error: nil, timedOut: true)) { @MainActor in .init(error: await fetching.fetchLastDisconnectError(id), timedOut: false) }`.
5. **`restoreOnDemand(ids)` = `settings.update { endOnDemandSuspension(ids) }; returnOnDemand(ids, thenConnect: nil)`** — same shape, one path.
6. **Crash grace switch:** `case .skip, .expectSystemRestart: restoreIfIdle()` (CS:906-910) — one branch, log the reason for both.
7. **`restoreCandidates()` once:** compute in `restoreIfIdle`, filter by `!othersBusy(except:)`, pass the list to `restorePaused` (kills N5 and the double computation).
8. **`holdsBackOnDemand`/`isBusy`/`mayMutateRunning`** are thin wrappers; after (3) only `holdsBackOnDemand` and `othersBusy` need to exist.
9. `addToPauseRecord([p.id])` in `restoreOne`'s failure path (CS:618) is needed only for `wantsRestore` candidates; comment it or add in `restorePaused` before the save for non-record ids so `restoreOne` has one responsibility.
