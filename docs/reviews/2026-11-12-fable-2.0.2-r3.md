# LockPlus 2.0.2 security review (Fable, round 3)

Scope: `git log 5c7fc7f3..cddbde38` (8 commits, HEAD cddbde38), read-only. Paths are relative to `native/` unless they start with `docs/`.

What this rests on: reading the fix diffs, the code around them, the new tests and DESIGN draft 10.6. I built nothing and ran no test; every finding below is from reading and none was reproduced. NE behaviour is taken from the project's notes.

## Verdict

No HIGH. One MEDIUM, four LOW, seven NIT.

- Both Codex HIGHs are closed for the scenarios Codex described, and each has a test that would catch a regression.
- The Auto-Connect seal (round 2 M1b) is only partly effective: on a Mac where no choice was ever sealed, and after Auto-Connect was turned off, a forged or replayed choice is still accepted (M1).
- The "never revoke a kill-switch record" trade is right. One hole in it can be closed: a user stop of a session that is already down never reaches the extension (L1).

## HIGH

None.

## MEDIUM

### M1. A forged or replayed Auto-Connect choice is still accepted in two common states (remaining, round 2 M1b)

**a. No choice was ever sealed on this Mac.**
- `App/Stores/ProfileRepository.swift:238`: no one-time value in the keychain means `.neverSealed`.
- `App/Stores/ProfilesStore.swift:160-162`: `.neverSealed` is "trusted once and sealed".
- `App/Stores/ProfilesStore.swift:134-137`: a disabled choice is never sealed, so the one-time value is created only when the user first turns Auto-Connect on under 2.0.2.
- So "once" is not once per Mac. It lasts until the first enable, which for a user who never uses Auto-Connect is forever.
- Scenario: same-user code writes `autoConnect {enabled: true, profileID: P}` (no tag) into `settings.json`, kills LockPlus and reopens it. The choice is trusted and sealed, P gets on-demand rules at the next re-save, and NE starts it unattended. This is the round 2 M1b attack, unchanged, for every user who has not enabled Auto-Connect under 2.0.2.
- `aChoiceFromBefore202IsTrustedOnceAndSealed` asserts exactly this behaviour on a fresh harness.

**b. Auto-Connect was turned off.**
- `ProfilesStore.swift:134-137`: turning it off clears the tag in `settings.json` but leaves the one-time value in the keychain.
- Scenario: same-user code copies `settings.json` while Auto-Connect is on for P. The user turns it off. The code writes the old `{enabled: true, profileID: P, choiceTag}` back and relaunches the app. The tag verifies and P has unattended consent again.
- A change to another profile does rotate the value, so only a withdrawn choice replays, not a re-pointed one.

Fix:
- Seal every state of the choice, including "off" (put the enabled flag in the message), so every change rotates the one-time value.
- Seal at the first 2.0.2 launch whatever the choice is. The keychain item's existence is then the "migration done" marker, which same-user code can't reset, and `.neverSealed` with an enabled choice happens only on the first launch after the update.
- Tests: a fresh 2.0.2 store that launched once with Auto-Connect off, then a forged enabled choice, gives no plan; a tag copied before "off" gives no plan after it.

## LOW

### L1. A user stop of a session that is already down never reaches the extension, so its kill-switch record stands until reboot (new in round 3, follows from the never-revoke rule)

- `App/Stores/ConnectionStore.swift:828-838` (`stopNetworkRestart`) and `:2054-2072` (`stop`): the user's Cancel or Disconnect calls `managers.stop(id)` only.
- If no provider is running (the `noNetwork` gap, a crash gap), NE delivers no `stopTunnel`, and the extension's `stop` with no session clears nothing (`TunnelController.swift:1310-1322`).
- Round 2 covered this with the idle revoke (`ConnectionStore.swift:1934`). That revoke now skips every kill-switch record (`TunnelController.swift:1347`).
- Scenario: a kill-switch Auto-Connect session, Auto-Connect turned off while it runs, then Wi-Fi drops. The app shows "connects when a network is available" and the user presses Cancel. The unattended record stays in `state.plist`. Until reboot, `scutil --nc start` by any local user is admitted as a replay with the owner's saved credentials, although the owner explicitly stopped the profile.
- docs/native/DESIGN.md:2494 says such a record "matters only to a replay with the same nonce". That is wrong for an unattended record.

Fix:
- Add an owner-only XPC call (or a `userStoppedProfileIDs` field on the revoke) that the app sends on every user stop: Disconnect, Cancel, Pause, Delete.
- The extension clears the whole record of that key, kill switch or not. This is the same authority as a user stop that reaches a live session, so it does not reopen Codex r2 #2: NE's restart was cancelled by the same user action.
- Test: `noNetwork` end, user Cancel, non-manual start gets 225.

### L2. One-shot intents are consumed only on success, so a record hidden at its moment can be replayed later (new in round 3; the rest of round 2 L5)

- `App/Stores/ManagerQuiescer.swift:81-89`, `App/Stores/ConnectionStore.swift:2291-2297`, `App/Headless/HeadlessResume.swift:178-181`: `consumeRecord` runs only when the check holds.
- Scenario (pause): same-user code copies the genuine pause record and, before the pause ends, changes `pausedState.profileID` in `settings.json`. The end of the pause fails the check, clears the record and does not consume the one-time value. Any time in the next 7 days the code writes the genuine record and `pausedUntil` back and relaunches LockPlus. The check holds and P is armed and started, for example after the user disconnected it on purpose.
- Scenario (update): the same with `pendingResume`. It has no age limit, so the window lasts until the next extension update seals a new record.
- docs/native/DESIGN.md §20 risk 29 (2) says the replay is fixed. It is fixed only when the genuine resume ran.

Fix: consume the kind's one-time value at every end of a pause and every `resumeAfterUpdate`, whatever the check says, except `.unavailable`. Tests: a failed check followed by the genuine record starts nothing.

### L3. A quarantined profile keeps its extension copy only until the next `load()` (remaining, Codex r2 #1 class; D10.6-7 overstates)

- `App/Stores/ProfilesStore.swift:969`: `existing` includes `tampered`.
- `App/Stores/ProfileRepository.swift:190, 320-322`: quarantine renames `<id>.json` to `<id>.json.tampered.<stamp>`, and `list()` reads only `*.json`. The next `load()` (every configuration change, every launch) no longer reports the ID.
- `ProfilesStore.swift:977-979`: the next reconcile then sends `removeProfile` with no check that the profile's session is live. `profileRemoved` clears the authorisation (`TunnelController.swift:1886`).
- Scenario: a connected kill-switch profile's metadata fails its MAC (same-user tampering, or a damaged file). After the next hello, or the next launch, its payload, credentials and start record are removed while the session runs. NE's next restart gets 225 and the Mac is open. Same outcome as Codex r2 #1.
- LOW because the trigger needs a tampered or damaged file, and same-user code can stop a VPN more directly. The Save Only case Codex described is closed.

Fix:
- Reconcile never removes the extension copy of a profile that is live, pending or held. Queue it in `pendingRemovals` until idle. Only `delete()` removes one, and it stops the session first.
- Make quarantine durable: have `list()` report IDs that have a `.tampered.*` file and no `.json`.
- Test: quarantine, a second `load()`, reconcile: no `removeProfile` for a live profile.

### L4. Timed-out reads can exhaust Swift's cooperative thread pool (new in round 3, from the L7 read timeout)

- `App/Stores/ImportCoordinator.swift:223-225`: a read that exceeds 10 s is abandoned, but its `Task.detached` stays blocked in `read()` on a cooperative-pool thread.
- Before the fix one hung read stopped the import and held one thread. Now the import moves on to the next file, and each hung file holds another.
- Scenario: `open -a LockPlus` with 20 files on a stalled network mount, repeated up to the queue cap. After about one hung read per CPU core, every non-main-actor task in the app stops: the profile repository (keychain, record checks), the validator client and the XPC decode paths.
- Same-user denial of service only. The pool-exhaustion mechanism is my reading of Swift concurrency, not something I ran.

Fix: do the read on a dedicated `Thread` or a private `DispatchQueue`, and stop reading the remaining files of an event after its first timeout.

## NIT

- **N1.** `TunnelController.swift:1377` with the test `aReplayWaitingInTheGuardPutsItsRecordBackAtAdmission`: the put-back also restores a record the user's stop cleared, not only one a revoke removed. With a duplicate configuration and a standing unattended record, an outside start queued during each session restarts the profile after every user stop. Revokes now skip guarded keys (`:1345-1348`), so the put-back is needed only for the legitimate duplicate. Skip it when the record went by a user stop, removal or wipe.
- **N2.** `TunnelController.swift:246-250`: if `kern.bootsessionuuid` can't be read in a fresh process, every record with a boot value is dropped and saved, which refuses NE's restart. Drop nothing when the current value is nil.
- **N3.** `TunnelController.swift:1395-1398`: the `killSwitch` upgrade from live flags is written only at an orderly end and only in memory (no save unless a summary is written). A crash leaves the admission-time value. Set it when the live flag is first seen and save.
- **N4.** `App/Stores/ManagerStore.swift:501-520`: a reload that finds nothing new silences every unknown object for 10 s, and a trigger suppressed in that window is never made up. If stale generations post status (S5), every ordinary connect opens that window. This can't hide a configuration change (`NEVPNConfigurationChange` still reloads), but it can delay the F7 note and the F8 re-classification indefinitely. Remember a suppressed trigger and reload once when the quiet ends.
- **N5.** `App/Stores/ImportCoordinator.swift:326-330`: `waitForNoSheet` re-queues its continuation without calling `watchSheets()` again. If another sheet appears between the wake-up and the re-check, the waiter never resumes, `analysing` stays above zero and no opened file is ever shown again. Call `watchSheets()` inside the loop. Separately, an opened import that started first can still present while the user's own analysis runs; hold it while `analysing > 1`.
- **N6.** `App/AppEnvironment.swift:325` with `App/Stores/ProfilesStore.swift:1107`: a profile verified by the launch's un-awaited pass, after reconcile computed its plan and before `provisionAfterVerify` is set, is not provisioned until the next reconcile. A GUI start heals it through the 221 retry; an on-demand start fails until then. Put such IDs into `provisionIncomplete`.
- **N7.** `LPXPCClient/ValidatorClient.swift:150-155`: a real crash of the retry within 2 s of the service's timeout is reported as a timeout. The profile stays "Not yet verified" and is never provisioned, so this is accuracy only. There is still no test for the exit timing (the fake never exits).

## Task 2: never revoking a kill-switch record

The trade is right. Keep it, and add L1.

**What a standing record gives an attacker.**
- Who: any local user, or same-user code, with `scutil --nc start` or System Settings.
- Precondition: an unattended kill-switch session, its rules removed while it ran (Auto-Connect off or re-pointed, Stay Connected off), then an end that was not a user stop reaching a live session, in the same boot.
- What: one non-manual start of the owner's own approved profile, to the owner's own server, with the saved credentials. No credential is disclosed, no other profile or server can be chosen, and nothing works after a reboot.
- How often: once per non-user end. A stop through `scutil` or the UI is a user stop and clears the record, so the attacker can't cycle it without a way to crash a root process.
- Effect: the Mac returns to the state the owner left it in (that tunnel up, kill switch on). The worst cases are that a kill-switch profile preempts the owner's current split session, or the network is blocked if the server is unreachable. Both are visible and end with one Disconnect. No traffic leaves outside a tunnel.

**What revoking costs.**
- The same precondition plus a revoke in NE's restart gap. The gap is seconds online and unbounded offline (lid closed, Wi-Fi roaming), and the app revokes at every settle, re-save and hello. Offline, the revoke lands in the gap almost every time.
- Effect: NE's restart gets 225, and an `includeAllNetworks` start that fails leaves the Mac open. Traffic leaves outside the tunnel, silently, while the owner believes the kill switch holds.

A visible, self-limiting nuisance against a silent loss of confidentiality: never revoking wins.

**What would be better.**
- L1's fix. It ends the record whenever the owner actually said stop, which is the only case where the standing record contradicts the owner's intent.
- Candidate, needs measuring first: end the record on stop reasons after which NE never restarts (`superseded`, logout and user-switch reasons, `providerDisabled`). Add E2E rows to see whether NE restarts after each; if not, treat them like `configurationRemoved`.
- I found nothing on the wire that tells NE's restart from an outside start, and no time limit is safe because the offline gap is unbounded. Clearing the unattended fact at a later armed start would be unsafe for the round 2 L4 reason.

## Task 3: the other areas the brief named

- **Record keys.** Per-kind HKDF keys from the keychain master key; the one-time value is in the app's access group; the comparison is constant-time. Same-user code can't forge a tag. The weak points are the life cycle (M1, L2), not the cryptography.
- **Trust-once migration.** Exploitable; see M1a. Pause and update records from before 2.0.2 are not trusted (`.olderRecord`, `.neverSealed` give no start).
- **In-process trust.** Settings are read from disk before `profiles.load()`, there is one `replaceAll`, and the UI write-back changes the choice only on a user edit. I found no way to turn a disk value into a "trusted" one except M1.
- **Boot binding.** Sound. N2 is the only edge.
- **Complement revoke and the 32 KiB cap.** Safe by construction: only records without a kill switch can go, and NE never restarts those. An app that sends an empty or wrong keep list loses nothing that matters. Over 500 keeps sends nothing, which is the safe side.
- **Reconcile split.** An unverified or stalled profile keeps its last approved copy until the user deletes it; the GUI and the agent refuse to start an unverified profile. That is not "provisioned forever" in a harmful sense. The quarantined case is L3.
- **Reload throttle.** Can't hide a configuration change; N4.
- **Check Again.** Resets counters and runs the same check; only an accepted verdict on the same revision and digest provisions. `verifyTimeoutRuns` is unauthenticated, but a forged value only stops or restarts retries.
- **Self-test.** The three Codex cases are closed and every unknown is inconclusive, never green. No new finding.
